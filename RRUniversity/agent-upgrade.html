Agent Upgrade Guide

GSI is moving the RapidReconciler administration console onto GSI’s own managed Azure gateway, and the RapidReconciler Agent on your application server is replaced as part of that move. This guide walks your IT team through it: the firewall and DNS rules to put in place first, how to download and swap the Agent, the browser permission your users need, and how to confirm data is flowing again afterward.

This document is the customer IT companion guide for the upgrade. Your team runs the steps; GSI is available on the call for any of them.

Overview

The RapidReconciler administration console moves off a legacy Microsoft-owned Azure address and onto GSI’s own managed Azure gateway. The new host presents a CA-issued certificate for a GSI-controlled domain rather than one under a shared Microsoft namespace.

What is changing

 BeforeAfter
Console URL https://rr-valc-spa.cloudapp.net/ https://rrvalcadmin-prod.getgsi.com/
Resolves to 168.62.49.184 20.81.98.127
Direction and port Outbound HTTPS, TCP 443 Outbound HTTPS, TCP 443
Certificate Shared Microsoft namespace CA-issued for a GSI-controlled domain

Traffic stays outbound HTTPS on TCP 443 in both cases, so no inbound rule is created and no new service is exposed on your network. Outbound TCP 8002 also has to be open — see 1. Firewall & DNS, which lists every endpoint the application server needs.

Who does what

  • Your teamThe firewall change, the Agent download, the uninstall and install on the application server, the browser permission, and the verification.
  • GSIAvailable on the call for any step. The installer comes from the RapidReconciler site itself, so there is no file to wait on from us.
  • Access neededLocal administrator on the application server, and whoever can change outbound firewall and proxy rules.

What is not affected

  • The RapidReconciler application itself, and the address your users type to reach it.
  • The RapidReconciler_Prod database, the SSIS package, and the nightly SQL Agent job. No work is required on the database server.
  • Your users’ accounts and passwords.
  • Inbound access. GSI does not initiate a connection into your network, before or after this change.

Expected downtime

RapidReconciler is unavailable to users between the start of step 3 and the end of step 4. On a server with the installer already downloaded, that is typically well under an hour. Steps 1, 2, 5 and 6 are all non-disruptive.

Order matters in one place

Finish step 1 and step 2 before starting step 3. Removing the working Agent before the firewall is open, or before the new installer is on the server, leaves reporting offline for as long as it takes to sort either one out.

Text for your change ticket

1. Outbound Firewall & DNS

Apply these rules on the server that hosts the RapidReconciler application services, and complete this step before the Agent is replaced. Every connection listed here is outbound only — GSI does not initiate a connection into your network.

Port change — TCP 8000 is no longer used

The RapidReconciler JMS service previously used TCP port 8000. It now uses TCP port 8002. If you already have an outbound rule naming rrjms-prod.getgsi.com:8000, update it — a rule that still names 8000 will not carry this traffic. Verified 2026-08-30: rrjms-prod.getgsi.com accepts a TCP connection on 8002 and refuses one on 8000.

Use hostnames where you can

If your firewall supports FQDN-based rules, write the rules against the hostnames above. An address rule stops matching when the address moves, and inside RapidReconciler that looks like a connectivity fault, not a firewall denial, so it is slow to find.

If your firewall needs IP addresses, use the column above, and keep in mind:

  • The four rr*-prod names share one address, 20.81.98.127. It belongs to GSI and has stayed the same since we started recording it in August 2026.
  • The two rapidreconciler names are served by Microsoft Azure App Service. Their addresses are shared with other Azure customers, and Microsoft can change them. One of them already has.
  • Before you file the change, run the Resolve-DnsName lines under Testing from the server below. If an answer differs from this table, use the answer and tell GSI.

DNS only — your RapidReconciler URL

Your site is assigned a hostname in the form rrprod-[companyname].getgsi.com. GSI creates and maintains that DNS record.

This one needs DNS resolution only. It does not need an outbound firewall rule, because the record points at the internal IP address of your own application server — the traffic never leaves your network.

Testing from the server

Run these from the server hosting the RapidReconciler components. PowerShell is the shortest route; nslookup works just as well for the DNS half.

1. DNS resolution

Resolve-DnsName rrvalc-prod.getgsi.com
Resolve-DnsName rrvalcadmin-prod.getgsi.com
Resolve-DnsName rrjms-prod.getgsi.com
Resolve-DnsName rrsso-prod.getgsi.com
Resolve-DnsName rapidreconciler-prod.getgsi.com
Resolve-DnsName rapidreconciler.getgsi.com
Resolve-DnsName rrprod-[companyname].getgsi.com

A successful result returns one or more IP addresses for each hostname. Substitute your own company name in the last line.

2. TCP port connectivity

Test-NetConnection -ComputerName rrvalc-prod.getgsi.com -Port 443
Test-NetConnection -ComputerName rrvalcadmin-prod.getgsi.com -Port 443
Test-NetConnection -ComputerName rrjms-prod.getgsi.com -Port 8002
Test-NetConnection -ComputerName rrsso-prod.getgsi.com -Port 443
Test-NetConnection -ComputerName rapidreconciler-prod.getgsi.com -Port 443
Test-NetConnection -ComputerName rapidreconciler.getgsi.com -Port 443

Omit the rrsso-prod test if you do not use the GSI SSO endpoint. There is no port test for rrprod-[companyname].getgsi.com — DNS resolution is all that is checked there.

3. All of them at once

This produces a single table you can paste straight into your reply to GSI, or attach to the change record.

$targets = @(
  @{ Name = 'rrvalc-prod.getgsi.com'; Port = 443 },
  @{ Name = 'rrvalcadmin-prod.getgsi.com'; Port = 443 },
  @{ Name = 'rrjms-prod.getgsi.com'; Port = 8002 },
  @{ Name = 'rrsso-prod.getgsi.com'; Port = 443 },
  @{ Name = 'rapidreconciler-prod.getgsi.com'; Port = 443 },
  @{ Name = 'rapidreconciler.getgsi.com'; Port = 443 }
)
$results = foreach ($t in $targets) {
  $r = Test-NetConnection -ComputerName $t.Name -Port $t.Port -WarningAction SilentlyContinue
  [pscustomobject]@{
    Endpoint = $t.Name
    Port = $t.Port
    Resolved = $r.RemoteAddress
    TcpOpen = $r.TcpTestSucceeded
  }
}
$results | Format-Table -AutoSize

Reading the result

The value that matters is TcpTestSucceeded, shown as TcpOpen in the combined table.

  • TrueOutbound traffic to that endpoint and port is permitted from this server. Nothing further is needed.
  • FalseThe connection is blocked, is not routable, or the destination cannot be reached from this machine. Test-NetConnection prints a WARNING line alongside the failure that separates a name which would not resolve from a port that would not open.
A passing port test is not a clean bill of health

Test-NetConnection opens a direct TCP socket and does not use a configured HTTP proxy. Where outbound web traffic is forced through a proxy or a secure web gateway, a False does not by itself mean RapidReconciler will fail, and a True does not prove it will succeed.

If your organization runs Zscaler, Netskope, Palo Alto Prisma Access, Cisco Umbrella or Forcepoint, read Zscaler & Gateways before you go any further. It has blocked RapidReconciler at two customer sites, and it passes every test on this page.

Zscaler and secure web gateways

If your organization runs Zscaler, read this before step 2. It has blocked RapidReconciler at two customer sites, and the failure looks exactly like a fault in the application.

The one that has actually bitten us

At two customer sites, users could not load RapidReconciler until their accounts were granted access to a Zscaler Private Access application segment for it. Everything else was configured correctly. This is the first thing to check, and it is a change your Zscaler administrator makes — not a firewall rule and not anything on the RapidReconciler side.

What it looks like

The application loads, or partly loads, and then no data appears. The giveaway is in the browser’s own developer console (F12, then the Console tab), where you will see a failure against your own RapidReconciler hostname on a high port number:

Failed to load resource: rrprod-[companyname].getgsi.com:37626/poll
net::ERR_CONNECTION_TIMED_OUT

The port will differ on your install; 37626 is one real example. Two things make this diagnostic reliable:

  • It is per userOne person cannot load RapidReconciler while a colleague on the same network can. A server-side or firewall problem affects everybody at once; this affects whoever has not been granted access.
  • It times outERR_CONNECTION_TIMED_OUT rather than a certificate error or a refused connection. The request is being absorbed, not rejected.
Virtual desktops are the usual place this appears

Where users reach RapidReconciler from a virtual desktop, that traffic goes through Zscaler even though both machines look like they are on your own network. A packet capture at one site confirmed the virtual desktop and the RapidReconciler server were not communicating on any other port — so there is no fallback path, and the high port either works or nothing loads.

Why RapidReconciler needs a high port at all

The page in the browser reads its data directly from the RapidReconciler application server, and each RapidReconciler database is served by its own process listening on its own high-numbered port. That is why the console error above names a port in the thirty-thousands rather than 443.

Those ports are assigned per database and are sticky — a given database keeps its port across restarts, so once the access is right it stays right.

What your Zscaler administrator needs to do

  1. An application segment covering RapidReconciler. It needs your RapidReconciler hostname, rrprod-[companyname].getgsi.com, and the service port for each RapidReconciler database. GSI will confirm the exact ports for your install — in practice they sit in the mid-30000s to mid-40000s. The segment name is yours to choose; something like RapidReconciler keeps it findable.
  2. An access policy rule granting your users. Zscaler Private Access denies access by default until a rule explicitly allows it, so the segment existing is not enough — the users or the group must be named in a rule that references it. This is the step described at both sites as “adding the users to the app segment”.
  3. Confirm the group actually synced. If your team cannot find the right group when writing the rule, it may not have synced to the Zscaler Client Connector Portal yet. That is a known snag and worth ruling out before assuming the group is wrong.
⚠ Adding a RapidReconciler database later means adding a port

Each database gets its own service port. If GSI adds a database for you after this is set up, its port will not be in the application segment, and users will find that one database will not load while the others are fine. Nothing will have changed on your network that day, which makes it a slow thing to spot. Tell your Zscaler administrator whenever a database is added, and tell GSI that Zscaler is in the path so we can flag it for you.

Confirming the fix

Have the affected user reload RapidReconciler with Shift + F5 and re-open the console. The /poll request should now succeed and data should appear. If a different high port then fails the same way, that is another database whose port needs adding to the segment.

A second, separate problem: HTTPS decryption

Zscaler and its equivalents can also decrypt outbound HTTPS for inspection. That is a different feature from the access control above, it breaks a different thing, and we have no record of it hitting a RapidReconciler install — it is here because the mechanism is real and it is cheap to rule out.

It would affect the Agent reaching GSI, not users reaching the application, and the signature is distinct: the step 1 port tests pass, a browser on the server reaches GSI without a warning, and the Agent log shows a certificate or SSL handshake error instead of a heartbeat.

To decrypt HTTPS, the gateway re-signs traffic with its own certificate. Every client has to trust that certificate. The standard rollout pushes the Zscaler Root CA into the Windows certificate store by Group Policy, and for almost everything on the server, that is the end of it.

The RapidReconciler Agent is a Java application, and Java keeps its own certificate store. It does not read the Windows one. The Agent runs on a Java runtime bundled inside its own install folder, so its trust list lives here:

C:\Program Files\Rapid Reconciler\jre\lib\security\cacerts

A Group Policy push that fixes every browser on the machine does not put anything in that file. Zscaler documents this pattern themselves, in their guidance for software developers, as a known cause of inspection breakage.

If that is what you have, the firewall is not the answer

Adding, widening, or re-testing firewall rules will not change it. The connection is being terminated and re-signed in the middle, and the Agent is refusing the certificate it receives. Both sides are working as designed.

Fix 1 — exempt the GSI hostnames from inspection (preferred)

Have whoever administers your gateway stop decrypting traffic to GSI’s endpoints. In Zscaler this means putting the hostnames in a custom URL category and setting the SSL Inspection policy action for that category to Do Not Inspect. Other products use different words for the same idea — a bypass, an exclusion, a do-not-decrypt list.

The hostnames are the ones in the step 1 table:

rrvalc-prod.getgsi.com
rrvalcadmin-prod.getgsi.com
rrjms-prod.getgsi.com
rrsso-prod.getgsi.com
rapidreconciler-prod.getgsi.com
rapidreconciler.getgsi.com

Why this one is better: it keeps working after an Agent upgrade. Upgrading the Agent replaces the bundled Java runtime, and a replaced runtime brings a fresh, empty certificate store — so fix 2 has to be redone every time, by someone who remembers it exists. An exemption is configured once, in your gateway, where your security team can see it.

Fix 2 — import the root certificate into the Agent’s Java store

If an exemption is not possible, add your gateway’s root certificate to the Agent’s own trust list. Your security team supplies the certificate file; run this on the application server as an administrator, with the Agent service stopped:

  # back up the store first
Copy-Item "C:\Program Files\Rapid Reconciler\jre\lib\security\cacerts" `
  "C:\Program Files\Rapid Reconciler\jre\lib\security\cacerts.backup"
 
  # import the root certificate your security team gave you
& "C:\Program Files\Rapid Reconciler\jre\bin\keytool.exe" -importcert -trustcacerts `
  -alias gateway-root -file C:\Temp\ZscalerRootCA.crt `
  -keystore "C:\Program Files\Rapid Reconciler\jre\lib\security\cacerts"

It will ask for the keystore password. Java’s default for this file is changeit. Answer yes when it asks whether to trust the certificate, then start the Agent service and check the log for heartbeats as in step 4.

This one expires without warning

Record that you did it, and where. The next Agent upgrade replaces the Java runtime and this import goes with it — the Agent stops connecting, and the reason is a change nobody made that day. If you take this route, put it in your own upgrade runbook, and tell GSI so we can flag it before the next upgrade.

Two smaller things the same gateway can do

  • Block the downloadThe Agent installer is not code-signed, and gateways commonly block or quarantine unsigned .exe downloads — sometimes delivering a truncated file rather than an error. If step 2 misbehaves, check the gateway’s log before assuming the download is broken. Ask GSI for the file’s SHA-256 hash to confirm what you received.
  • Drop port 8002The JMS connection on TCP 8002 is not web traffic, and a gateway that proxies web traffic may drop a non-standard port outright — a firewall rule permitting 8002 does not change that. Symptom: the Agent reaches GSI but the connection never settles. This needs the port allowed at the gateway, not just at the firewall.

What to tell GSI

These answers let us rule the whole area in or out in one message instead of three:

  • ProductWhich gateway or proxy is in the path, and whether it is Zscaler Private Access, Internet Access, or both.
  • App segmentWhether a RapidReconciler application segment exists, which ports it covers, and which users or groups are granted access to it.
  • UsersWhether your users reach RapidReconciler from virtual desktops. If so, say so early — that is where this has bitten.
  • InspectionWhether HTTPS decryption is switched on for the application server, and whether the GSI hostnames and TCP 8002 are exempted.
  • EvidenceFor a user-side failure, the browser console output. For an Agent-side one, the newest rr-valc-agent_YYYYMMDD.out.log. Either settles which of the two problems you have.
Nothing here weakens your security posture

Granting named users access to one internal application, or exempting a handful of hostnames you already permit through your firewall, is narrower than loosening anything broadly. Traffic stays encrypted end to end — an inspection exemption only stops your gateway from opening and re-sealing it in the middle.

3. Stop and uninstall the current Agent

Run these steps on the application server, signed in as a local administrator. RapidReconciler is unavailable to users from here until step 4 finishes.

3.1 — Keep a copy of the current logs

Optional, and worth the two minutes if you have an open support thread. Copy C:\Program Files\Rapid Reconciler\logs\ somewhere outside the install folder. The uninstall removes it.

3.2 — Stop the Windows service

  1. Open services.msc.
  2. Find Rapid Reconciler 7 Agent (service name rr-valc-agent) and stop it.
  3. Open Task Manager and confirm no java.exe processes remain. The Agent owns one child process per RapidReconciler database, and stopping the service ends all of them.
Use the service, not Task Manager

Stop the service and let it shut its children down. Ending java.exe processes by hand can leave the Agent’s local state mid-write, which turns a clean uninstall into a support call.

3.3 — Run the uninstaller

  1. Run C:\Program Files\Rapid Reconciler\unins000.exe as administrator. The same entry appears in Apps & features if you prefer to start it from there.
  2. Follow the prompts through to completion.
  3. Confirm the rr-valc-agent service no longer appears in services.msc. You may need to refresh the list.
  4. Confirm C:\Program Files\Rapid Reconciler\ is gone. If a few files remain because something held them open, delete the folder by hand.
Nothing reportable is lost

The Agent keeps only its own local working state on disk — deployment history and queue identifiers. All of your RapidReconciler data lives in SQL Server, which the uninstall does not touch, and the new Agent rebuilds its local state on first start.

4. Install the new Agent

  1. Run the installer as a local administrator on the application server.
  2. Accept the default install path, C:\Program Files\Rapid Reconciler\, unless GSI has told you otherwise. That path is referenced in support procedures.
  3. Let the installer finish and register the service.
  4. Open services.msc and confirm Rapid Reconciler 7 Agent shows Running with startup type Automatic.
  5. Open Task Manager. You are looking for one process for the agent plus one for each RapidReconciler database, but they take several minutes to all appear — step 6 shows the finished state and how to count them. Do not read a low count at this moment as a failure.

Confirm the Agent has reached GSI

Open the newest dated log in C:\Program Files\Rapid Reconciler\logs\ — the file named rr-valc-agent_YYYYMMDD.out.log — and look for a repeating pair of lines roughly every 30 seconds:

INFO c.r.agent.jms.ValcOutbound : Sending heartbeat. States: [ ... ]
INFO c.r.agent.jms.ValcOutbound : Sending company sync

Each heartbeat carries one entry per database, and each entry should read up=true. A heartbeat every 30 seconds with up=true throughout is a healthy Agent.

Connection errors during the first minute are expected

Health-check failures appear for a few seconds per database while each child process starts its listener. They matter only if they continue with no heartbeat following them.

If there is no heartbeat at all

The usual cause is step 1. A reconnect loop, or a failure to connect at all, points at outbound access to rrvalc-prod.getgsi.com:443 or rrjms-prod.getgsi.com:8002 — port 8002 in particular, if a rule still names 8000. Re-run the port test from step 1 on this server and send GSI the result along with the newest .out.log.

If that port test passes and there is still no heartbeat, read the log before anything else. A certificate or SSL handshake error there means the problem is not the firewall — see the HTTPS-decryption half of Zscaler & Gateways. That combination, ports open and the Agent refusing the certificate, is the one that costs a day.

5. Allow local network access in the browser

RapidReconciler runs in the browser and reads its data from the Agent on your own network. Recent Edge and Chrome versions gate that with a permission. Where the site is not allowed, users sign in successfully and then see empty screens with no error.

Do this on one workstation before you tell users the change is complete, then include it in whatever you send them.

Which address to add — the same answer in both browsers

Add the address your users actually type. For most sites that is rapidreconciler-prod.getgsi.com; some sites are served by rapidreconciler.getgsi.com, and some reach the application through their own rrprod-[companyname].getgsi.com hostname. Adding more than one entry does no harm, so if your users reach RapidReconciler by more than one address, add each of them.

Microsoft Edge

  1. Open Edge Settings.
  2. Go to Privacy, search, and services → Site permissions → All permissions → Local network.
  3. Leave Default behavior on Ask before accessing (recommended). There is no need to change it.
  4. Under Customized behaviors there are two blocks. Look at the lower one, Allowed to access other devices on your local network.
  5. The address your users type to reach RapidReconciler should appear there. If it is missing, click Add site beside that block and add it.
  6. Check the upper block too, Not allowed to access other devices on your local network. If the address is sitting in that one, remove it there first — a block entry wins, and the prompt will not come back on its own.

Google Chrome

Chrome calls the permission Local network as well, and its page carries the same Default behavior and Customized behaviors sections. Only the route to reach it differs.

Do not pick “Apps on device”

Chrome’s permission list holds Local network and Apps on device next to each other, and they are two different things. Apps on device governs access to other apps and services running on the same machine. RapidReconciler needs Local network — access to other devices on your network, which is what your application server is from the user’s workstation. Granting the wrong one changes nothing and looks like the permission did not help.

Setting it for RapidReconciler

  1. Open the Chrome menu (the three dots at the top right) and choose Settings.
  2. Type local network into the Search settings box at the top. This is the quickest route, and it is version-proof — Chrome has reorganized where this permission sits more than once.
  3. Open Local network from the results. The full path, if you prefer to navigate to it, is Privacy and security → Site settings → Permissions → Additional permissions → Local network.
  4. Leave Default behavior on Sites can ask to access other devices on your local network. There is no need to loosen the default for every site.
  5. Under Customized behaviors, find the Allowed to access other devices on your local network list.
  6. Click Add site beside that list, enter the address your users type to reach RapidReconciler, and save.
  7. Confirm the address now appears under Allowed to access other devices on your local network, and not under Not allowed.

The prompt users may see instead

If you leave the default in place rather than pre-adding the site, the first user to open RapidReconciler on that workstation gets a prompt reading Access other devices on your local network, with three buttons:

  • Allow this timeGrants access for this visit only. The prompt returns on the next visit, so this is the option that generates support calls. Tell users not to choose it.
  • Allow while visiting the siteThe one to choose. Access persists for RapidReconciler, and the site lands in the allowed list on its own.
  • Never allowBlocks it. A user who clicks this, or dismisses the prompt repeatedly, will see empty screens from then on with no further prompt.
If a user has already blocked it

The prompt does not come back on its own. Open the same Local network page, look under Customized behaviors for the address in the Not allowed to access other devices on your local network list, remove it from there, and add it to the allowed list instead. Then reload RapidReconciler with Shift + F5.

Checking it from the site itself

You do not have to go through Settings to see the current state. With RapidReconciler open, click the icon to the left of the address in the address bar, then Site settings. The permission appears in that list as Local network, and can be set to Allow there directly. That is the fastest check when a single user reports empty screens.

If the permission is set and data still does not appear

Two different things produce the same empty screen. Open the browser console (F12 → Console) on the affected workstation. If you see ERR_CONNECTION_TIMED_OUT against your rrprod-[companyname].getgsi.com hostname on a high port number, this permission is not the problem — the request is being stopped before it reaches your server. Go to Zscaler & Gateways. The tell is that it affects some users and not others.

Rolling it out by policy

Where your organization manages browser settings centrally, this permission can be pushed by policy rather than set on each workstation. That is the better route for a site with more than a handful of RapidReconciler users, and it removes the permission from the list of things a new starter has to be told about.

Chrome exposes two policies for it, both taking a list of URL patterns:

  • LocalNetworkAccessAllowedForUrlsSites listed here get local network access without prompting. This is where the address your users type to reach RapidReconciler goes.
  • LocalNetworkAccessBlockedForUrlsSites listed here are refused. Check that no existing broad pattern in this policy already covers RapidReconciler, since a block entry wins.

Edge is built on the same engine and carries equivalent policies. Whoever manages your browser policy will recognize both from the standard administrative templates.

Why this permission exists at all

Browsers added it so that an arbitrary website cannot quietly probe the devices on your network. RapidReconciler is caught by it because it does something a public website normally should not: the page in the browser reads its data from a server inside your own network. Granting the permission for one address you control does not loosen anything for any other site.

6. Confirm you can see data

Give it several minutes before you check anything

The agent and its data-services processes take several minutes to finish starting. Until they have, RapidReconciler signs in normally and shows nothing. That is the install still coming up, not a fault, and it is the single most common reason this step gets reported as failed.

Watching the processes start

Task Manager is the progress indicator. On the application server, open Task Manager and count the entries named Java(TM) Platform SE binary:

  • At least 2One for the agent itself, plus one for each RapidReconciler database. A single-database install settles at two.
  • More databasesAdd one process per database. Four databases means five processes — the agent plus four.
  • Still climbingThey appear one at a time as each database comes up. A count below your expected total means it is still working, so wait and count again.

Once the count is right, carry on with the checks below. If it has not reached your expected total after ten minutes, go back to the heartbeat check in step 4 before doing anything else — a process that never appears will have said why in the log.

The checks

Work through this from a normal user’s workstation, not from the application server, so the browser permission from step 5 is exercised the way a user will exercise it.

  1. Open RapidReconciler and sign in.
  2. Confirm your company list is populated. An empty company selector is a data-path failure, not a permissions one.
  3. Open a page that reads real volume — the Reconciliation page for a loaded period is the fastest check — and confirm rows appear with amounts on them.
  4. Check the System Status light in the page header. Click it if it is red; RapidReconciler downloads a SystemStatus_....xlsx report showing the status of last night’s data load.
  5. Export something to Excel. That exercises a different path from the on-screen grid and is worth confirming before your users find it for you.

If you sign in but see no data

Work these in order, quickest first.

  • Startup timeCheck this first. Count the Java processes on the application server again. If they have not all appeared, nothing else on this list is the cause and the wait is the answer.
  • NetworkConfirm the workstation is on the office network, or connected by VPN.
  • Hard reloadPress Shift + F5 to reload past any cached copy of the page.
  • Browser permissionRe-check step 5 on this specific workstation. The permission is per browser profile, so it is set for the person who set it and not for the machine.
  • AgentOn the application server, confirm the rr-valc-agent service is running and the newest .out.log is still writing heartbeats.
  • Firewall and proxyRe-run the port test from step 1 on the application server. A rule applied to the wrong host or the wrong port shows up here.
  • ZscalerCheck this before the ones above if only some users are affected. Open the browser console (F12) on an affected workstation. A ERR_CONNECTION_TIMED_OUT against your own rrprod-[companyname].getgsi.com hostname on a high port means the user has not been granted access to the RapidReconciler application segment. See Zscaler & Gateways.
Still no data

Email rrsupport@getgsi.com with the port-test table, the newest rr-valc-agent_YYYYMMDD.out.log, and which of the checks above you have already run. Sending those three together removes a round trip.

Backout & support

Backout

The two halves back out separately.

  • Console addressRevert the documented URL and bookmarks. The legacy address stays reachable until GSI decommissions it.
  • The AgentReinstalling the previous Agent version is a GSI-assisted step, not a local one, because the previous version has to be supplied and its registration re-established. Open a thread with rrsupport@getgsi.com rather than reinstalling from an older copy you happen to still have.

The outbound firewall rules can be left in place either way. They permit outbound HTTPS to GSI-controlled hosts and expose nothing on your network.

What to send GSI

  • Test outputThe port-test table from step 1, run on the application server.
  • Your RR hostnameConfirmation that rrprod-[companyname].getgsi.com resolves, and the address it returned.
  • ProxyWhether outbound traffic from the application server passes through a proxy, and whether that proxy inspects TLS.
  • SSOWhether you use the GSI SSO endpoint, which decides whether rrsso-prod.getgsi.com applies to you.
  • Agent stateConfirmation that the Agent is running and sending heartbeats after step 4.
Re-test after any later firewall change

These rules are checked once and then assumed. If your team changes firewall policy, replaces an appliance, or moves the application server to a different network segment after this upgrade, run the combined script from step 1 again. It takes seconds, and it rules the network out first.
