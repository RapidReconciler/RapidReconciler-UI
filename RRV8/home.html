Purge old data

Move the start date forward and the next refresh permanently removes everything before it — the same cutoff is applied to every company at once, so you don’t have to edit them one by one.

Current start date
—
Database file size
—
Companies don’t share the same period beginning dates. Review the fiscal calendars before purging — the cutoff may not line up the same way across every company.
This is permanent. Once a new start date takes effect on the next refresh, all data before it is purged on the server — you can’t go back without a full reset. Strongly recommended: have IT back up the database first. There is no other recovery.

Why purge? Large databases cause real problems

  • Performance — queries and refreshes slow down as history piles up.
  • Disk space — the database file can grow until it fills the drive.
  • tempdb — big operations can exhaust tempdb and crash the server.
  • Autogrowth — frequent file growth fragments the database and stalls writes.

Reload GL data

When the account roll-forward shows a GL break that posting batches won’t clear, this clears RapidReconciler’s copy of the general ledger from the earliest broken period forward. JDE re-pulls it on the next scheduled refresh — RapidReconciler never pulls from JDE on its own.

Reload cardex data

When the perpetual cardex won’t roll cleanly and the variance won’t clear, this clears RapidReconciler’s copy of the cardex (F4111) and its transaction detail from a date you choose forward. JDE re-pulls it on the next scheduled refresh — RapidReconciler never pulls from JDE on its own.
