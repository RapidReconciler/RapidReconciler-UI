What VALC 2.0 modernizes

VALC 2.0 collapses the install into a single Manage Client wizard and replaces the manual steps that the legacy flow required. The two biggest shifts:

  • Import from email populates Client Details, JDE configuration, Topology, and the server cards in one paste — no field-by-field transcription from the submission.
  • Generate install bundle mints the per-install identity and packages the download(s) by topology. The old hand-delivered agent is gone — it's assembled when you click the button. (The administrator account is created later, at the go-live handoff, not in the bundle.)

Topology auto-fills from the agent's heartbeats once it reports in, and the Databases tab discovers RapidReconciler_* databases on the customer's SQL Server so you pick from a list instead of typing connection details. The steps below walk the full wizard in order.

About the Process

Setting up a new customer in VALC 2.0 and getting them live is a three-phase process:

  • VALC entry (Steps 1–4) — Working from the pre-install submission, you create the client (Client Details), record the Topology, and click Generate install bundle — which mints the per-install identity and packages the download(s) by topology.
  • Customer install (Steps 5–6) — The customer runs the agent installer on the application server while the database team runs the SQL scripts and deploys SSIS on the SQL Server, concurrently. VALC's Install Progress surfaces the connectivity checks.
  • Completing setup (Steps 7–10) — Registering databases, verifying they're Online, licensing company numbers, and customer handoff.

Agent Deployment Constraints

Two architectural rules that shape every install and migration:

  • One agent per customer network. Only a single instance of the RapidReconciler Agent should be installed on the customer's internal network. Multiple agents pointing at the same VALC client record will compete and produce inconsistent state.
  • One agent supports multiple databases. A single agent can serve any number of RapidReconciler databases (Prod, Test, Dev, Train) — including databases hosted on different SQL Servers. Each database is registered separately in VALC (see Step 7) but they all communicate through the same agent.

What the RR Agent Transmits to GSI

The agent maintains an outbound-only connection from the customer's application server to GSI's VALC infrastructure (256-bit encrypted; no inbound traffic to the customer's network). It transmits the following data, used to keep VALC's view of the customer environment current and to support licensing and version control:

Knowing what the agent reports back is useful when answering customer security questions, when explaining why a value appears in VALC without being entered there manually, and when triaging mismatches between the customer's environment and what VALC shows.

VALC 2.0 update — how the agent is identified

In VALC 2.0 the agent is recognized by a per-install client id and secret baked into its application.properties at bundle time, not by its external IP. On each connect the agent presents the id + secret; VALC resolves the client and verifies the secret against a stored hash. This means the Agent External IP Address becomes telemetry only — VALC refreshes it automatically every time the agent reconnects (about every 30 seconds), so a customer's WAN IP can change without anyone calling in the new address and without VALC losing the connection. Agents from older installs that carry no client id still fall back to external-IP identification until they're re-bundled.

About VALC

VALC (Version and Licensing Control) is the VALC 2.0 control plane — a GSI-operated web application that runs as a containerized (Docker) service on GSI-managed Linux infrastructure. It is used to manage RapidReconciler customers. All new customers must be added to VALC before the installation process can begin.

Important

Adding a customer in VALC is performed by GSI staff only. Operator sign-in is moving to Microsoft Entra ID single sign-on in a future update.

Login URL: The VALC login URL is provided to authorized GSI staff and is not published in this knowledge base. Use the login credentials provided to you by GSI.

Step 1 — Pre-Install Submission

The pre-install submission email is requested by Sales once the contract is signed — it is not a tech step. Sales sends the customer the Tech Installation Prep guide, the customer's I/T contact works through it, and the completed submission lands at rrsupport@getgsi.com. Your work begins when that submission arrives. It contains every value you need to set up the client correctly on the first pass — topology, server names and internal IPs, source platform, JD Edwards connection details, and a complete environment readiness checklist.

Do not start without this email

The submission is the trigger for your work. If you haven't received it, check with Sales that it was requested after the contract was signed. Setting up the client from a partial discovery call risks recording the wrong server names or IPs, which causes rework once the customer installs at Step 5.

One submission feeds the whole install

The same submission drives both halves of the install. You use it to create the VALC client record (Step 2), record the topology (Step 3), and generate the install bundle (Step 4) — which packages the database bundle the database team runs on the SQL Server. There is no separate “database-ready” hand-off to wait on: the database install and the VALC setup both flow from this one submission and the bundle you generate from it.

The submission lands in the rrsupport@getgsi.com inbox with a subject line of the form RapidReconciler Pre-Install Submission — {Customer Name}. A real example is shown below.

What replaced the old Add Client popup

The legacy Add Client popup asked for HTTPS, Agent Protocol (SSL), Maximum Companies Allowed, and an Agent IP Address. Those fields are gone in VALC 2.0: HTTPS and the broker protocol are baked into the install bundle, the license count is enforced by which company numbers you license at Step 9, and the agent's IP is telemetry that arrives with its heartbeats — nothing to type here.

Step 3 — Topology

The Topology tab records the customer's server layout so VALC knows where the agent runs and where the databases live. If you used Import from email at Step 2, the configuration and server cards are already populated — confirm them here.

Server Configurations

The submission's Topology Selected value maps to one of three configurations:

ConfigurationLayout
Configuration 1Co-located — Database, SSIS, and Application all on a single server.
Configuration 2Separate Database + SSIS server and Application server (two servers).
Configuration 3 (legacy)Older three-box layout with a separate SSIS server. Retained for existing installs only — new installs use Configuration 1 or 2.
The JDE source is always required

Regardless of configuration, every install reads from a JD Edwards source on a separate server — it’s a requirement, not a topology choice. The Topology tab shows the JDE Source card (host, database, login, table qualifier) for every configuration; capture it from the customer’s submission.

Application Server Card

The Application Server card holds the customer's domain URL (e.g. rrprod-customername.getgsi.com) and the application server's internal IP. These are the values the agent and the DNS check (Step 6) depend on.

Auto-fill from heartbeats

Once the customer installs the agent (Step 5) and it reports in, the Application Server card auto-fills from the agent's heartbeats — hostname, OS, Java and agent versions, internal and external IP, and last-seen time populate without anyone clicking a button. Where a value you entered differs from what the agent reports, VALC surfaces the detected value inline so you can adopt it.

JDE Source Card

The JDE Source card records how RapidReconciler reaches the customer's JD Edwards source database — the system the data load extracts from. It captures the JDE server name or IP, the JDE database (SQL Server source only), and the JDE login and password (the read account). It appears for every topology, since every install has a JDE source to pull from. The source platform (Oracle / AS’400 / SQL Server), the table qualifier, and the data-dictionary decimals are not on this card — they live on Client Details under JDE Configuration.

Confirm the server cards match the submission, then click Save & Next to continue.

One JDE source per client — with a rare per-database exception

The JDE Source card is per-client: every database under that client extracts from it. For the uncommon case where one database must read from a different JD Edwards connection — a second JDE instance on the same box, or a non-SQL (Oracle / AS’400) source you supply as an OLE DB connection — the SSIS configuration step (Step 4) carries an optional Override JDE source for this database panel. Leave it closed for the common case. A non-SQL override is validated and its decimals are read by the on-box agent at run time rather than from VALC.

Step 4 — Generate Install Bundle

This is the centerpiece of the VALC 2.0 install. With Client Details and Topology confirmed, click Generate install bundle. One action does what the legacy flow did by hand — minting the agent's identity and assembling the download(s) the customer needs. (The administrator account is created later, at the go-live handoff — not in the bundle.)

What the button does

  • Mints a per-install identity. A unique client id and secret are generated and baked into the agent's application.properties. This is how VALC 2.0 recognizes which customer an agent belongs to — it replaces the old reliance on the customer's external IP. The secret is stored only as a hash.
  • Packages the download(s) by topology (see below) and emails the customer the matching one-time download link(s).
  • Carries no sign-in. The bundle installs the agent only — it does not create the customer's administrator account or any password. The RapidReconciler administrator is seeded later, at Customer Handoff (Step 10), and receives a set-password link by email. (In the legacy flow the bundle minted an RRAdmin@<domain> temp password in RR-FIRST-LOGIN.txt; that step is gone.)

Bundle layout by topology

TopologyBundle(s) produced
Configuration 1 (co-located) One combined bundle containing an app-server/ folder (the agent installer) and a sql-server/ folder (the SQL scripts + SSIS package + README). Everything installs on the single server.
Configuration 2 / 3 (separate servers) Two separate bundles: an agent bundle for the application server (WinSW + bundled JRE + agent + Services jar + cert), and a database bundle for the database team (the four SQL install scripts + the SSIS .dtsx package + a README), run on the SQL Server.
When SSIS is on its own server (Configuration 3)

The dedicated SSIS server gets no separate delivery. Its package rides in the database bundle and is deployed to its catalog from the SQL Server. There is no third download.

How the customer receives it

VALC emails the customer a one-time download link for each bundle — the customer doesn't log in to a portal to fetch it. For Configuration 1 that's a single link; for Configuration 2/3 the agent bundle goes to the application-server owner and the database bundle to the database team. The bundle carries no sign-in credential — the administrator's set-password link is emailed separately at Customer Handoff (Step 10).

Step 5 — Customer Installs (Agent + Database)

These two halves run in parallel, not in sequence

The agent install and the database install are independent. Have the customer's application-server admin and the database team both available so the two halves run concurrently — neither waits on the other to finish.

Agent install (application server)

The customer runs the agent installer from the agent bundle on the application server. It lays down WinSW, a bundled JRE, the agent and Services jar, and the customer certificate. On first start the agent phones home to VALC using its baked-in client id and secret, then heartbeats roughly every 30 seconds. Within a heartbeat or two, the client's Agent pill on the dashboard turns green and the Topology tab's Application Server card auto-fills from the reported facts (Step 3).

The bundle carries no sign-in. The administrator account is seeded and emailed a set-password link later, at Customer Handoff (Step 10), once the customer's company data is showing.

Database install (SQL Server)

Concurrently, the database team runs the database bundle on the SQL Server: the four SQL install scripts in SSMS, then VALC deploys the consolidated SSIS project (.ispac) into the server's SSISDB catalog from the Deployment Center. The bundle's README walks the order. This is documented in full in the companion guide.

One-time SSISDB catalog prerequisites (per SQL Server)

RapidReconciler V8 deploys and runs its data load from the SSISDB catalog — the same model most existing customers already run. Three things must be in place on each SQL Server before VALC can deploy:

  • CLR integration enabled — the catalog's stored procedures are CLR-backed (sp_configure 'clr enabled', 1; RECONFIGURE;, sysadmin). SSISDB's assemblies are Microsoft-signed, so clr strict security can stay on.
  • The SSISDB catalog created, with its master key backed up. Create it once in SSMS (Integration Services Catalogs → Create Catalog — tick "Enable CLR integration" and set a master-key password), as a sysadmin. Record the master-key password and back up the catalog master key — restore SSISDB without it and the encrypted connection passwords are lost.
  • SQL Server Agent running, its service account a member of SSISDB ssis_admin. Catalog operations reject SQL Server authentication (Msg 27123) and on-premises SQL Server has no Entra option, so VALC routes every catalog deploy and the scheduled load through a SQL Agent job step — which runs under the Agent's Windows service account. Grant it once: USE SSISDB; CREATE USER [<agent account>] FOR LOGIN [<agent account>]; ALTER ROLE ssis_admin ADD MEMBER [<agent account>];

Step 4 of the Installation flow checks all three (Check SSIS) before you build the environment and deploy.

Step 6 — DNS / Connectivity Check

For the customer to reach RapidReconciler over HTTPS, the application server's domain URL must resolve to its internal IP. This is the same domain URL and internal IP recorded on the Topology tab's Application Server card (Step 3).

DNS ‘A’ record

  1. Have GSI I/T add an ‘A’ record for the customer's *.getgsi.com domain pointing at the application server's internal IP.
  2. This ensures the application UI uses the *.getgsi.com certificate. Allow time for DNS propagation.

Install Progress checks

VALC's Install Progress checklist surfaces two connectivity signals you watch here:

  • Agent reachable — turns positive once the agent's heartbeats arrive (from the customer's install at Step 5).
  • Domain resolves to app server — confirms the domain URL resolves to the application server's internal IP.
Needs-action flag

A running client whose domain does not resolve to its app-server IP is flagged as needs-action on the dashboard. Resolve the DNS ‘A’ record before moving on — the customer can't reach the UI until the domain points at the right IP.

Step 7 — Register Database

With the database installed on the SQL Server (Step 5) and the agent reporting in, you register each RapidReconciler database with VALC so a Services instance can run against it.

Add Database is a picker, not free text

  1. Open Manage Client → the Databases tab.
  2. Click Add Database. Instead of a free-text form, a dropdown picker lists the RapidReconciler_* databases the agent discovered on the client's SQL Server — RapidReconciler_Prod, and any _Test / _Dev / _Train that exist.
  3. Pick a database to register it. Connection details (address, port, credentials) are derived from the Topology server cards — there's nothing to retype per database.
  4. Start its service with the ▷ (play) control on the row. VALC assigns a service port and launches the per-database Services instance; the row comes Online.
Why a picker

The picker only offers databases that actually exist on the customer's SQL Server, so you can't register a typo'd or non-existent name. If a database you expect isn't in the list, confirm the database team created it from the database bundle (Step 5) and that the agent has reported in.

Adding a Test, Dev, or Train database

Don't re-run the database creation scripts — they're coded with RapidReconciler_Prod references. Instead, on the SQL Server back up RapidReconciler_Prod and restore it under the new name (RapidReconciler_Test, etc.). Once it exists, the agent discovers it and it appears in the Add Database picker, ready to register the same way.

If the customer rotates the rruser password

Every install ships with its own unique rruser password. If the customer's DBA later changes it, the agent can no longer authenticate — connections fail with Login failed for user 'rruser'. The customer can't update VALC themselves, so ask them to send the new password by encrypted email, then update it on the client's Topology tab. The change is picked up on the next poll — no restart needed.

Step 8 — Verify Databases Online

On the Databases tab, confirm that every registered database shows Online. Online means the database has a running Services instance on its assigned service port — the row is live and ready to feed data.

Pending vs. Online

A Pending row is registered but has no running service yet — start its service with the ▷ control on the row (Step 7). Company numbers do not appear on the Companies tab until the corresponding database is Online, so resolve any non-Online rows before licensing at Step 9.

If a row won't go Online, see Troubleshooting — the usual culprits are the agent not yet reporting in, a stopped Services instance, or a database-server reachability problem.

Step 9 — License Company Numbers

With the database showing Online, the customer's JDE company numbers become available on the Companies tab. Licensing each company number the customer purchased is what enforces the contract's license count.

  1. Select the Companies tab.
  2. From the database dropdown at the top-left, select the database whose companies you want to license. The list of company numbers below updates to reflect that database.
  3. Check the applicable company numbers in accordance with the purchase agreement.
Note

If more than one RapidReconciler database has been registered for this client, company licensing must be completed for each database separately. Use the database dropdown to switch between them.

Step 10 — Customer Handoff

With licensing complete and the agent loading data, the last step is the go-live handoff: hand the environment off to the customer's RapidReconciler administrator so they can set up their team and start using the application. VALC does this for you — you don't hand-write any credentials.

Wait for company data to show first

The Install tab's Install Progress panel includes a “Company data is showing” check. It turns green once the customer's RR Service has loaded their JDE company data. The Hand off to customer button stays disabled until it does — handing off before the data lands would drop the administrator into an empty app.

Running the handoff

On the Install tab, the Go-live handoff card sits at the bottom. It shows the RR Administrator (the customer's Contact 2 — name + email) and the customer's app URL. Once “Company data is showing” is green and an RR Administrator email is on file, click Hand off to customer. VALC then:

  • Seeds the RR Administrator account — the Contact 2 email, with the Administrator role across the client's databases. (Set the RR Administrator on Client Details first if it isn't on file; it's required to hand off.)
  • Emails the welcome message to that address: the app URL plus a one-time link to set their password (valid for 7 days). There is no temporary password — the administrator sets their own via the link.
  • Marks the client Live — the card flips to “Live since …” and a green Live pill appears on the Clients grid. (Need to re-send? The button becomes Resend welcome email, which mints a fresh link.)

If SMTP isn't configured on this VALC, the welcome email (with the link) is still recorded in the email audit — relay it to the customer manually.

Per-Database User Permissions

User permissions in VALC 2.0 are scoped per (user, database) — set on the User Accounts tab. The administrator chooses which companies and tabs each user can see for each database the user is granted. This is the customer administrator's ongoing responsibility once they're live.

Confirm with the Customer

After the handoff, confirm the customer has used the set-password link and signed in at least once. The administrative confirmation is to check the User Accounts tab for that client and verify the administrator account shows recent activity.

What's Now the Customer's Responsibility

Once the handoff is complete, the customer's RapidReconciler administrator owns:

  • Adding and removing user accounts for their team
  • Setting per-database user permissions on the User Accounts tab
  • Resetting passwords for users who get locked out (see Password Policy for the procedure)
  • Day-to-day use of the application

GSI continues to own the underlying environment — VALC configuration, agent and database health, server-side updates, and the kinds of changes captured in Common Requests.

  • Customer ran the agent installer on the application server (agent heartbeating; Agent pill green)
  • Database team ran the SQL scripts and deployed SSIS on the SQL Server (concurrently)
  • Domain resolves to the app-server internal IP; Install Progress connectivity checks pass

Completing Setup (Steps 7–10)

  • Each RapidReconciler_* database registered from the Add Database picker and its service started
  • All registered databases show "Online" on the Databases tab
  • Company numbers licensed per the purchase agreement (for each registered database)
  • “Company data is showing” check green; Hand off to customer run — RR Administrator seeded + welcome email sent; client shows Live
  • Administrator used the set-password link and signed in at least once

The Deployment Center

The Deployment Center is the single console for standing up and maintaining a customer’s RapidReconciler databases. It has three tabs — Installations, Upgrades, and Troubleshooting — each working one customer (and usually one database) at a time. Every tab is laid out as numbered, top-to-bottom bands, so you work straight down the page.

Installations tab vs. the install bundle

The Generate Install Bundle workflow (Steps 1–10) is the bundle-based install — the customer’s database team runs the SQL scripts on their own SQL Server. The Installations tab is the alternative VALC-driven path: VALC connects to the target SQL Server with a privileged account and creates the database, schema, and login itself. Where a customer’s DBA won’t allow VALC to run CREATE DATABASE directly, the Build preview is the exact SQL for them to review and run by hand.

Installations Tab

Installs a customer’s database — a new customer’s first install, or an additional database for an existing one. New customers awaiting their first install sort to the top of the picker. Work down the seven bands:

  1. Which customer? Pick the customer; the summary shows what they already have installed.
  2. Readiness Check. Connects to the target SQL Server and verifies the environment is ready. Open the Connection panel to enter the sysadmin account that will perform the install — on a cold install, rruser doesn’t exist until Deploy creates it. The password is used for the check only and is never stored. Then Run checks.
  3. Install a Database. Name it (the RapidReconciler_ prefix is locked; the suffix defaults to Prod) and pick the install release. Build previews the create-database + schema + rruser SQL, Test confirms the account can create it and the name is free, and Deploy creates the database, publishes the schema, creates rruser (idempotent — a no-op if it already exists), and registers it.
  4. SSIS Package Configuration and Deploy. Per database: ① pick the database; ② Build environment resolves its SSISDB catalog environment and checks it’s complete; ③ Check SSIS verifies the catalog is ready (CLR enabled, SSISDB present, SQL Agent running with its account in ssis_admin); ④ Deploy package lands the .ispac in the catalog; and ⑤ Validate runs a real SELECT 1 against both the JDE source and the RR database. The catalog project is shared across every database on that SQL Server, so a database can show the package as already present (deployed by a sibling database) with no recorded version — the step turns amber and offers a one-click Package Deploy to stamp this database’s own version so it can be shown and compared.
  5. Bootstrap and Licensing. Bootstrap companies loads companies + period cutoffs only — a quick first pass that seeds the company list. Then tick the companies to license; each writes straight to the customer’s licensing list, and the server applies the contract’s seat limit and reserved-company rules. License the companies before the full data load.
  6. Load Staging Data. A SQL Server Agent readiness line shows before you start — the load runs as the database’s SQL Agent job, so a stopped Agent is flagged here (with Re-check) rather than failing the run. Load Data pulls the bounded transaction history (best run off-hours); the nightly schedule keeps it current afterward. Watch Load Progress and the Tables row counts fill; Stop load halts a run (leaving a partial load you’d normally clear and reload).
  7. SQL Agent Job Schedule. Set the nightly steady-refresh run time and turn the schedule on — it defaults to daily at 02:00. Run refresh now seeds the data immediately instead of waiting for the next scheduled run. A DBA can still set a different cadence (weekly, specific days) in SQL Server Agent; this card sets the time + on/off and shows whatever cadence is configured.

Upgrades Tab

Moves an existing customer’s database, Services jar, and SSIS package forward — one customer and one database at a time. The Step 1 picker shows each database’s current DB / Services / SSIS version with an update available pill wherever one is behind.

  1. Which customer & database? Pick the customer, then pick the one database to upgrade — the rows are selectable and show where that database stands on all three release lanes. The release bands below track the selected database (green when a lane is already current). When a customer is fully current, a Re-deploy anyway button unlocks a forced re-push or repair.
  2. Database. Pick a release for the Step 1 database. Build diffs the release against it and previews the exact SQL (Export .sql for long scripts), Test is a dry-run reporting what would change plus any data-loss warnings, and Deploy publishes it. By default a data-loss change is blocked; Allow data loss permits it, but only after you’ve reviewed the pre-flight.
  3. Services. Pick a Services release and Deploy it to the database picked in Step 1 (Services run per database). Services can be rolled back to a prior version from here.
  4. SSIS Package. Pick a package version and Deploy — it lands the .ispac in the SSISDB catalog and (re)creates that database’s SQL Agent job. Re-deploy is idempotent. The per-customer connections come from the catalog environment you build on the Installations tab.
Rolling a database back isn’t a reverse-deploy

A database release can’t be cleanly undone — schema changes aren’t reversible, so deploying an older release is blocked as data loss. To back out a bad database release, restore from backup or apply a forward-fix. Services is the exception: it rolls back from the Services step.

Troubleshooting Tab

Read-only diagnostics for one customer database, run straight from VALC — the agent log, SSIS last execution, B→C reconcile log, and all-company roll-forward, plus an ad-hoc SQL band. It’s the first stop for a production issue. See Troubleshooting for the per-band walkthrough.

Troubleshooting

Diagnostic patterns for the most common install problems. The Deployment Center's Troubleshooting tab is the first stop — it reads the agent log, SSIS status, and roll-forward for a chosen database straight from VALC; the raw agent log file is the deeper fallback.

This section covers the most common failure modes encountered during a client install and in production. Each entry lists the symptom, the most likely causes, and the steps to remediate. If a problem isn't covered here or remediation steps don't resolve it, escalate to the GSI database administrator or a senior tech.

Diagnostic Tools

The Deployment Center Troubleshooting Tab

Most of the checks below can now be run from VALC itself, without remoting into the customer's server. In the Deployment Center, the Troubleshooting tab — the third tab, alongside Installations and Upgrades — gives you read-only diagnostics for one customer database at a time. Start here before reaching for the raw log files.

Pick a customer and one of its databases in Step 1, then open whichever band you need:

  • Agent Log — pulls the customer agent's live out.log and runs the same rule-based triage as the standalone log analyzer: a verdict, the concerning lines lifted to the top, and benign noise suppressed. The Full analyzer link opens the complete tool in a new tab.
  • SSIS Catalog — the last package execution for that database (status and timing), so you can confirm the JDE import is actually running.
  • System Status — the recent B→C reconcile cycles with per-cycle analysis. Export to Excel saves the full log.
  • Account Roll Forward — the GL and variance roll-forward summary across all companies, with an Excel export for the analysis workbook.
  • Ad-Hoc Queries — run a curated maintenance script (version-controlled in the RapidReconciler-DB repo) or type SQL against the Step 1 database, then read the result set and row counts back inline.

The four diagnostic bands (Agent Log, SSIS Catalog, System Status, Account Roll Forward) are read-only; Ad-Hoc Queries runs whatever SQL you give it against the selected database. When the tab can't tell you what you need — or the agent isn't connecting at all — fall back to the raw log files below.

Agent Log Files

The RapidReconciler Agent writes detailed log files on the customer's application server. These are the primary source of truth for diagnosing connectivity issues — when a scenario below says "check the agent logs," this is where to look.

Location: C:\Program Files\Rapid Reconciler\logs\

What's there:

  • rr-valc-agent_YYYYMMDD.out — daily output log. Open today's file (matching the current date) to see recent agent activity. Most connectivity diagnostics live here.
  • rr-valc-agent_YYYYMMDD.err — daily error log. Inspect alongside the .out file when the agent is reporting issues.
  • rr-valc-agent.wrapper — service wrapper log. Useful when the agent service itself isn't starting.

Double-click the .out file to open it in the default text viewer. Scroll to the bottom for the most recent entries.

Tip

If you're diagnosing remotely, ask the customer's IT contact to send you the latest .out file rather than transcribing errors over a call. The full log usually contains more context than any single error message they'll quote.

Database Status: Unknown or Stopped

Symptom: On the Databases tab, a row shows Unknown or Stopped (or Pending) instead of Online. See Step 8.

Tell them apart:

  • Stopped usually means the database has never connected since being registered in VALC. The Revision Number column is typically blank — no revision has been reported back yet.
  • Unknown usually means the agent had previously reached the database (so a Revision Number is populated) but has since lost contact.

Likely causes:

  • Connection details derived from the Topology server cards are wrong — IP, port, username, or password don't match what's actually on the customer's SQL Server
  • RR Agent service on the customer's application server is stopped or has lost network access
  • Firewall on the database server is blocking the agent's connection on the configured port
  • The physical database doesn't exist on SQL Server (registration in VALC succeeded but the underlying database wasn't created or has been removed)
  • SQL Server Authentication is disabled or the rruser login was not created

Remediation:

  1. Verify the connection details on the client's Topology server cards match the actual database — see Step 3, and confirm the database is registered and its service started at Step 7.
  2. Confirm the RR Agent service is running on the customer's application server. If not, start it.
  3. Check today's agent .out log file (see Diagnostic Tools above) for connection errors or stack traces.
  4. From the application server, attempt a manual connection to the database server on the configured port (e.g., telnet 10.x.x.x 1433) to confirm reachability.
  5. Confirm the customer's DBA has created the RapidReconciler_Prod database and the rruser SQL Authentication login.
  6. If everything looks correct and status remains failed, escalate to the GSI database administrator.

Companies Tab is Empty

Symptom: Database shows Online on the Databases tab, but selecting it from the dropdown on the Companies tab shows no company numbers to license.

Likely causes:

  • The first sync from JDE has not yet completed — Online status confirms VALC can reach the database, but company numbers are populated from JDE through the SSIS package's first run
  • The SQL Agent job is not running or is disabled on the database server
  • The SSIS package's source connection (to JDE) is misconfigured, even though the destination (to RapidReconciler_Prod) is working
  • (verify) The customer's JDE environment has no companies in the source tables that the SSIS package reads

Remediation:

  1. On the Companies tab, check the Last Company Sync timestamp at the top-right. If it shows recent activity, give the sync a few more minutes to complete and refresh the page.
  2. On the database server, verify the RapidReconciler SQL Agent job is enabled and has run successfully at least once.
  3. Check the SQL Agent job history for errors on the most recent run.
  4. If the job is failing or has never run, escalate to the GSI database administrator to investigate the SSIS package and JDE connection.

Clients Grid Row Not Updating to Connected

Symptom: Agent install reported Installation Complete, but on the VALC Clients grid the row's Status badge stays at the previous value (e.g., Disconnected or whatever it was before install) instead of switching to Connected.

Likely causes:

  • DNS for the customer's .getgsi.com subdomain has not yet propagated after Cloudflare update
  • The rr-valc-agent service (display name: Rapid Reconciler 7 Agent) is installed but not running
  • VALC has not refreshed — the underlying agent has connected but the grid row hasn't updated yet
  • Agent External IP on the Client Details tab does not match the customer's actual external IP

Remediation:

  1. Refresh the Clients grid in your browser (the page does not auto-refresh). Wait a few minutes if the install just completed.
  2. From the customer's application server, try resolving the customer's .getgsi.com URL — if DNS still returns the old IP, the Cloudflare update hasn't propagated yet. See Server Migration for the Cloudflare contact and process.
  3. On the application server, open the Windows Services console and confirm Rapid Reconciler 7 Agent (service name rr-valc-agent) is Running. There is only one service to look for — the agent supervises one java.exe per RR database, which appear in Task Manager but not in the Services console.
  4. Verify the Agent External IP Address on the Client Details tab matches the customer's actual external IP.
  5. If the row still hasn't updated, check today's agent .out log file (see Diagnostic Tools above) for connection errors back to VALC.
VALC 2.0 update — external-IP mismatch no longer applies

The "Agent External IP doesn't match" cause and remediation step above are specific to the legacy external-IP identity model. In VALC 2.0 the agent identifies itself by its baked-in client id + secret, and VALC refreshes the stored external IP automatically on every connect — so a changed WAN IP no longer keeps a row from going Connected, and there's nothing to verify or edit by hand. If a VALC 2.0 agent isn't connecting, focus on DNS propagation, the Windows service state, and the agent .out log instead.

Setup Step Not Advancing

Symptom: After completing an install or migration, the Setup Step field on the Client Details tab remains at Created (or an earlier value) and does not advance automatically.

Background: The Setup Step field tracks where a client is in their lifecycle. Created is the state required for the agent to display the install prompt on first login (see Server Migration). After install completes successfully, it should advance — but in some cases the state needs to be moved manually.

Remediation:

  1. Confirm the install actually completed end-to-end: agent installed, database Online, connectivity row showing Connected.
  2. If all of the above are good, manually advance the Setup Step on the Client Details tab to the appropriate next value (verify which value the field expects after install).
  3. If you're not sure what value to set, check another active client for reference.

Cloudflare Update Made but Data Not Appearing

Symptom: Cloudflare has been updated by the GSI network admin and confirmed propagated, but data still doesn't appear in the customer's RapidReconciler UI.

Likely causes:

  • SQL Agent job schedule is not yet enabled (this is the last step in Server Migration and is intentionally deferred until after Cloudflare confirmation)
  • SQL Agent job is enabled but has not yet had a chance to run on its schedule
  • SSIS package connection strings still point to the old server (after a migration)
  • Browser cache or session is showing stale data

Remediation:

  1. On the database server, confirm the SQL Agent job schedule is enabled, then trigger a one-time manual run to validate.
  2. Check the job history for errors.
  3. Have the customer log out and log back in, or hard-refresh their browser.
  4. If the issue is post-migration, double-check SSIS package connection strings on the new server.
Diagnostic Quick-Reference

When a customer reports "RapidReconciler isn't working," the fastest triage path is usually:

  1. Check the customer's row on the VALC Clients grid — Status, Services version, Agent version, System Status.
  2. Open Manage Client > Databases tab — confirm Online for every registered database.
  3. If both look healthy, the issue is likely on the JDE-side data flow (SQL Agent job, SSIS package).
  4. If either looks unhealthy, work backward from the failed signal using the relevant section above.

Password Policy

The complex password policy: requirements, login, reset, administration, and how to flip the per-customer toggle.

RapidReconciler supports an optional complex password policy that can be enabled per client by the GSI tech team. When enabled, all user passwords for that client must conform to the requirements below. The policy is designed to protect sensitive financial reconciliation data and align with common enterprise security standards.

Password Requirements

When the complex password policy is enabled, all user passwords must meet the following criteria:

RequirementDetail
Minimum length8 characters
Name restrictionCannot contain the user's account name or parts of their full name exceeding two consecutive characters
Password historyCannot match any of the last 10 passwords
ExpiryMust be changed every 90 days
Storage & transmissionMust not be displayed, stored, or transmitted in clear text

Character Complexity

Passwords must contain characters from at least three of the following four categories:

  • English uppercase characters (A through Z)
  • English lowercase characters (a through z)
  • Base 10 digits (0 through 9)
  • Non-alphabetic characters (e.g. !, $, #, %)
Tip

A strong password example would be Blue$ky92 — it contains uppercase, lowercase, a digit, and a special character, and does not resemble a name or a previously used password.

Logging In

When a user attempts to log in, they will be directed to the Password Reset screen if either of the following conditions is met:

  1. 90 days have elapsed since their last password change.
  2. They click the "Forgot your password?" link and then follow the reset link sent to their email.
Note

The password reset link sent by email is time-limited. If the link has expired, the user should repeat the "Forgot your password?" process to receive a new link. If the issue persists, contact the customer's RapidReconciler administrator.

Resetting a Password

On the Password Reset screen, the new password must conform to the policy outlined above. The Confirm button remains disabled until the password meets the 8-character minimum length requirement.

Common reasons a new password may be rejected:

  • The password is fewer than 8 characters
  • The password does not meet the three-category complexity requirement
  • The password contains the user's name or account name
  • The password matches one of the last 10 previously used passwords

Administration

Assigning a Temporary Password

The customer's RapidReconciler administrator can assign a temporary password to a new user. On first login, the user will be required to reset the temporary password before gaining access to the application.

Best Practice

When assigning a temporary password, notify the user through a separate communication channel (e.g. phone or a separate email) rather than including the password in the same message as the login instructions. This reduces the risk of unauthorized access.

Enabling or Disabling the Password Policy

The complex password policy is enabled or disabled at the client level via the Password Policy toggle on the Client Details tab in VALC (see Step 2). When disabled, users are not subject to the complexity, history, or expiry requirements described above.

Recommendation

It is strongly recommended to keep the complex password policy enabled in all production environments to protect access to sensitive financial data.

Locked or Inaccessible Accounts

If a user is unable to log in and cannot complete the password reset process (e.g. they no longer have access to the email address on file), the customer's RapidReconciler administrator can assign a new temporary password directly through the User Accounts section in VALC.

Requesting Activation

Customers request activation of the complex password policy by emailing GSI support. The GSI tech team enables the Password Policy toggle on the client's Client Details tab once the request is processed.

The customer's email to rrsupport@getgsi.com should include:

  • Company name and RapidReconciler account details
  • The name of the customer's RapidReconciler administrator
  • Requested activation date
Note

It is recommended to notify all users in advance before the policy is enabled. Existing users will be required to reset their passwords at their next login once the policy is active.

Server Migration

Migrating an existing client to new infrastructure is its own multi-phase procedure with two distinct topology paths (dedicated server vs. separate application + database servers). It’s documented in detail as a standalone guide.

See Server Migration for the complete procedure — covers both topologies, the VALC and Cloudflare cutover, and the post-migration verification checklist.

Quick orientation on what’s in that guide:

  • Dedicated Server — agent and database on the same machine. Five sequential steps: backup/restore database, migrate SSIS package, recreate SQL Agent job, install RR agent, capture IPs.
  • Separate Servers — app server and database server flows run in parallel, then converge.

SQL Scripts (Developer Reference)

Developer-only tool for applying SQL update scripts across customer databases. Tech support uses this rarely; included for completeness.

SQL Scripts (Developer Reference)

Intended Audience

This page documents the SQL Scripts page in VALC, which is reserved for RR developers. The GSI tech team responsible for client installs does not normally use this feature. This section is included here as a single self-contained reference for the team that does.

The SQL Scripts page provides a controlled way to apply update scripts (schema changes, data fixes, patches) across customer databases without logging in to each customer's SQL Server directly. A developer selects which databases to target, chooses an update script, and executes — pass/fail results are reported back inline.

Page Layout

The page is divided into three working areas:

AreaPurpose
Database list (left)Lists all databases registered across all customer clients in VALC, formatted as {ClientName} - {DatabaseName} - {RevisionNumber}. Each row has a checkbox for selection.
Filters (top-left)Database Selection filters the list by the database's Category (Production, Test, Archive, Change Control, Inactive). Revision Number is a freeform text field — type any portion of a revision number to filter the list to matching rows.
Script editor (top-right)Choose File opens a file browser to select the update script provided by the developer (typically a .sql file from the local filesystem). Once a file is selected, its text appears in the dark editor area for review. EXECUTE runs the script against the selected databases.
Results panel (bottom-right)Displays a pass/fail line per database after execution completes.

Process

  1. Filter the database list as needed using the Database Selection dropdown and/or the Revision Number field. Filtering narrows the list so it's easier to find the right targets without accidentally checking the wrong row.
  2. Select the databases to update by checking the box next to each row.
  3. Choose the update script using the Choose File button. The script's contents will appear in the dark editor area — review it before proceeding.
  4. Click EXECUTE to run the script against all selected databases. Wait for the run to complete; pass/fail results will populate the Results panel.
Recommendation

Limit each execution to 5 databases at a time. Running a script against too many databases in a single execution increases the chance of partial failures, makes the Results panel harder to read, and complicates rollback if something goes wrong. For larger rollouts, batch the work into multiple executions.

Best Practices
  • Always review the script contents in the editor area before clicking Execute, even if you trust the source.
  • Run scripts against a Test database first when possible, then promote to Production after verification.
  • If a script fails on one or more databases, investigate the cause before re-running on the same targets — re-executing a partially-applied script can compound the problem.
