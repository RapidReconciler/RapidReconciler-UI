Overview

The RapidReconciler database is the per-customer SQL Server database that everything else on the platform reads from and writes to. The SSIS package (SSIS Package Spec) loads JD Edwards source data into it; the Services jar serves the V8 UI out of it; the nightly cycle reconciles inventory against the GL inside it. There is one database per customer environment (e.g. RapidReconciler_Prod, plus optional Test/Train), and it is fully rebuildable from JDE — it holds no system-of-record data of its own.

  • Source of schema: the SSDT project RapidReconciler.sqlproj in the RapidReconciler-DB repo, built to a RapidReconciler.dacpac (desired-state artifact).
  • Login: rruser — the least-privilege application + load login (SSIS writes as it, the Services jar reads as it).
  • Deploy: the Deployment Center applies the dacpac per customer via SqlPackage, which diffs the dacpac against that customer’s live schema and generates the exact upgrade script (so drift is handled, not assumed).
  • Recovery: SIMPLE — the database is reloaded from JDE, so point-in-time log recovery is not needed (§5).

This spec is the database-side companion to the SSIS Package Spec (how data gets in) and the Services Documentation (the jar that serves the data out). The three are the V8 install: DB + SSIS + Services, on top of the frozen legacy broker.

2. Load → reconcile pipeline (“A to B to C”)

A refresh is two stages, and the database is involved in both. The names come from the legacy run: A→B is the extract, B→C is the reconcile.

// A to B  — the SSIS package (see SSIS Package Spec)
JDE source  →  F-tables / Staging_*        // extract + net-change MERGE

// B to C  — T-SQL, inside the RR database
EXEC dbo.usp6_001_run_b_to_c
   → usp6_002_set_up          // rebuild RCompanies, account lists, fiscal calendar
   → usp6_006_inventory       // load + reconcile inventory from the cardex
   → usp6_007_merge_cx_gl     // merge cardex and GL accounts
   → usp8_txv_classify        // classify the cardex-vs-GL residual into cards
   → usp6_009_account_summary // RAccountSummary (the recon grids read this)
   → usp6_009a_in_transit / usp6_009b_rnv   // if those modules are licensed
   → usp6_010_clean_up        // finalize RunHistory, trim RServer_Log

usp6_001_run_b_to_c is the top-level entry point. It opens a run header in RunHistory, runs the reconcile procs in sequence (purging aged history first if a retention boundary has passed), and finalizes in usp6_010_clean_up. Every step logs into RServer_Log (§4).

The SSIS load alone does not make RR usable. A→B fills the F-tables; it is B→C (usp6_001_run_b_to_c) that populates the reconciliation output the UI reads, and that writes RunHistory / RServer_Log. The scheduled job runs both stages in order (§11); the Deployment Center’s Step-6 staging load is the A→B half only.

2a. B→C execution map (procedure → objects)

A working reference for the entire B→C chain: every procedure and sub-procedure in execution order, with the persistent tables it reads/writes and the views it drives. Built to answer three questions as we walk it one procedure at a time in execute-SQL mode — which objects are actually used, are the tables indexed correctly, and do the views perform. Pure logging helpers (usp6_update_server_log / usp6_update_trans_results) are omitted. Table 3 holds first-pass observations; per-procedure findings get appended as we go.

Sub-procedures are indented under their parent. Writes are tagged with the operation. usp6_008a_customizations is customer-reserved (see §9 / deploy notes) — it is never shipped in an update script. Purges (rows 1–4) are conditional — they run only when a retention boundary advances, and are normally skipped.

3. Net-change apply (the usp8_apply_* procs)

The transactional tables (cardex, GL, batch control, item branch, receipts) are loaded by a dumb pipe + set-based MERGE: SSIS FASTLOADs the windowed pull into a Staging_* table, then a versioned proc MERGEs it into the live F-table. The proc — not SSIS — does the new/changed (and for the GL, deleted) detection. This is the database half of the refactor described in SSIS Package Spec §9.

TableApply procShape
F0911 (GL)usp8_apply_f0911insert + update + delete (window-scoped, self-derived); parity-verified byte-identical to the old SSIS logic
F4111 (cardex)usp8_f4111_build_change_pull + usp8_apply_f4111new rows by watermark; changed = re-pull still-open rows by ILUKID, MERGE-update (RF4111ChangeBatchType holds the self-derived watch-set)
F0011 (batch)usp8_apply_f0011insert + update (iciapp, icist), no delete
F4102 (item branch)usp8_apply_f4102insert + update + self-heal delete (de-licensed / out-of-cardex item-branches); license-scoped pull
F43121 (receipts)usp8_apply_f43121insert + update (11 status cols on the 9-col PK), no delete; F0101 join for the address-book name

Each proc writes one row to dbo.RSsisLoadLog (§4) recording its new/changed counts — the durable per-run record the console reads, because an SSIS Execute SQL task cannot surface a T-SQL PRINT to the catalog log.

These are not catalog objects, so they ship with the dacpac like any other proc — only the SSIS .ispac needs the special catalog deploy. Full per-table parity contracts live in docs/plans/ssis-staging-merge-refactor.md.

5. Recovery model & file policy

The database runs SIMPLE recovery. It is reloaded from JDE on a schedule, so there is nothing a transaction-log backup chain would protect that the next load doesn’t rebuild — and FULL recovery would fully-log the multi-million-row F-table loads, which is slow and grows the log without bound.

SIMPLE is enforced three ways so it is correct no matter how the database came to exist:

  • The creation script sets it at CREATE DATABASE.
  • The SSDT project model carries <RecoveryMode>Simple</RecoveryMode>, so a publish never emits SET RECOVERY FULL at the top of the deploy script — which matters because the publish’s F-table index rebuilds (§6) would otherwise run fully-logged.
  • PostDeployment.sql re-asserts SIMPLE on every publish (idempotent), self-healing a DB that inherited FULL from model or an earlier install.

Log autogrowth is a fixed 512 MB increment, not a percentage. A percentage-growth log autogrows in ever-larger, blocking, zero-filled chunks; a fixed increment is predictable and cheap. PostDeployment.sql converts any percentage-growth log to 512 MB on publish.

Availability Groups are the exception: an AG member database must be FULL recovery. The SIMPLE default needs an explicit carve-out for AG installs — tracked with the install-docs work, not yet reconciled. FCI and standalone targets are unaffected.

6. Keys & IGNORE_DUP_KEY

The 23 non-bootstrap F-table primary keys carry IGNORE_DUP_KEY = ON (everything except the four bootstrap/company tables F0006, F0008, F0010, F41001). A resumed or overlapping load can re-pull rows that straddle the previous window boundary; with IGNORE_DUP_KEY the duplicate insert is silently tossed instead of failing the whole load on a PK violation.

First upgrade to this build rebuilds those PKs. IGNORE_DUP_KEY can’t be toggled in place — SqlPackage drops and recreates each affected primary key, which rebuilds the clustered index and every nonclustered index on that table. On the 7M-row F4111 and 6.5M-row F0911 this is the bulk of the first publish’s time. It is a one-time cost (subsequent publishes match) — and on SIMPLE recovery (§5) it runs minimally-logged, which is the whole reason the recovery model matters at deploy time, not just at load time.

7. Engine floor SQL 2019 — compatibility level pinned at 140

RapidReconciler requires a SQL Server 2019 or later engine. Separately, and on purpose, every object must run at compatibility level 140: the V8 install and every upgrade run ALTER DATABASE … SET COMPATIBILITY_LEVEL = 140 so the optimizer behaves identically on every customer regardless of which engine version they bought. These are two different requirements. A 2022 engine pinned to 140 is the normal, tested configuration — raising the level to match the engine is not an upgrade, it is a change to every query plan.

Allowed (compat 140): STRING_SPLIT, STRING_AGG, TRIM, CONCAT/CONCAT_WS, IIF, OFFSET/FETCH NEXT, TRY_CAST/TRY_CONVERT, cumulative SUM() OVER (ORDER BY), JSON functions, CREATE OR ALTER, DROP … IF EXISTS. Still forbidden (above the pinned level; every one of them is a SQL 2022 feature): GREATEST/LEAST, GENERATE_SERIES, STRING_SPLIT(…, enable_ordinal), DATE_BUCKET, the native json type.

Why the list exists even though the build catches most of it. Measured on a real SQL 2019 engine, one procedure per construct: GREATEST, LEAST and DATE_BUCKET are rejected at CREATE time (Msg 195), and three-argument STRING_SPLIT with Msg 8144 — the procedure is never created, so publishing the dacpac to a 2019 engine catches them on its own. GENERATE_SERIES does not behave that way. It is a table-valued function, so deferred name resolution lets the procedure create cleanly and it fails only when the procedure runs, with Msg 208. That one is caught by the source scan alone, which is why the written list is a gate and not a courtesy.

8. Versioning

The database version is the string 8.0 beta.N, stamped into two stores that the platform reads:

  • the extended property RapidReconciler.DatabaseVersion (the Services jar reads this first);
  • the RSystemVariables row DatabaseVersion (fallback + legacy sprocs).

PostDeployment.sql stamps both from a DatabaseVersion SQLCMD variable whose default lives in RapidReconciler.sqlproj. The bump-db-version GitHub Action increments the beta number on every merge to main that touches RapidReconciler/**.

The bump action uses a custom [skip-bump] marker, not [skip ci] — GitHub honors [skip ci] on tag pushes too, which would silently skip the release build.

9. Deploy model

The database ships as a dacpac — a desired-state artifact, not a frozen migration script. The Deployment Center applies it per customer with SqlPackage, which diffs the dacpac against that customer’s current live schema and generates the exact upgrade script at deploy time. Drift (an extra index, a hand-added column) is reconciled, not assumed away.

StepWhat happens
1. Create(New install) the creation script makes the database SIMPLE-recovery with fixed file growth.
2. PublishSqlPackage applies the dacpac — tables, procs, views, and (first time) the IGNORE_DUP_KEY PK rebuilds (§6).
3. Post-deployPostDeployment.sql stamps the version, asserts SIMPLE, and fixes log autogrowth.
4. rruserThe least-privilege login is created/granted (incl. VIEW SERVER STATE so it can read SQL Agent state for the console).

The dacpac covers tables, procs, views, and the Staging_*/usp8_* net-change layer — everything except the SSIS .ispac, which is a catalog object and deploys its own way (SSIS Package Spec §13).

Every object must be in the .sqlproj build manifest to ship. The project is a classic SSDT .sqlproj (explicit Build Include items, no glob), so a net-new .sql applied to dev via sqlcmd is not in the dacpac until its <Build Include> line is added. Audit before cutting a release.

10. Cutting a release (manual steps)

A database release is a tag-triggered dacpac build, parallel to the Services jar release flow. The version stamp is automatic (§8); cutting the release is a tag + a sync.

  1. Land the change on main. Merge the PR. The bump-db-version Action advances RapidReconciler.sqlproj to the next 8.0 beta.N and pushes a chore: bump db version commit. Confirm main’s <DefaultValue> shows the version you intend to release.
  2. Tag it. Create an annotated tag db-v8.0-beta.N on the bump commit and push it. The tag prefix db-v* is what fires the build.
  3. Build. release-dacpac.yml runs on the self-hosted dev-box runner (classic .sqlproj needs the VS2022 SSDT build targets), builds RapidReconciler.dacpac, and attaches it to a GitHub Release named DB 8.0 beta.N. Watch the Action; the runner must be online.
  4. Sync into VALC. In the Deployment Center’s Manage Deploy modal, click Sync from GitHub for the database component (or POST /api/v1/file-versions/sync-from-github?component=database). VALC pulls the dacpac into file_versions (component database); it then appears as the latest DB release in the deploy picker.

XML-comment gotcha: an MSBuild project file is XML, so a comment in RapidReconciler.sqlproj cannot contain -- (error MSB4025). A double-hyphen in a rationale comment fails the dacpac build on the runner.

The Services jar uses semantic versioning (0.2.0) and a v* tag on the Agent repo — see Services Documentation. The SSIS package uses ssis-v8.0-beta.N — see the SSIS Package Spec. All three sync into the same VALC file_versions catalog.

11. Scheduling (the SQL Agent jobs)

A live customer runs the refresh on a schedule via SQL Server Agent. The legacy model is a single job (RapidReconciler_Prod) with two steps and a daily schedule:

StepSubsystemCommand
Run A to BT-SQLA SSISDB catalog.create_execution of the package (the staging load).
Run B to CT-SQLEXEC dbo.usp6_001_run_b_to_c (the reconcile cycle, §2).

Both steps must run for a refresh to be complete — A→B fills the F-tables, B→C produces the reconciliation the UI shows. The schedule ships disabled so it never fires before the install is finished.

V8 Deployment Center model (in progress): Step 7 of the Installations flow provisions two jobs — an Initial Load (one-time, the first full historical pull + reconcile) and an RR Refresh Cycle (nightly steady refresh) — both disabled on creation, with the nightly Refresh gated behind a successful Initial Load. The run-result cards read RunHistory, RServer_Log, RSsisLoadLog (§4), and the SSIS catalog execution views.

12. SQL coding conventions (case, collation & comments)

Two pressures shape how objects are written: a new DBA has to be able to read them, and a customer may host RR on the same SQL Server instance as JD Edwards, which requires a case-sensitive server collation. The conventions below serve both.

Collation — a CI database that tolerates a CS server

RR objects assume a case-insensitive database. Two layers keep that true even when a customer puts RR on a case-sensitive-server instance (the JD Edwards coexistence case):

  • The database is pinned CI at creation. The creation script sets COLLATE SQL_Latin1_General_CP1_CI_AS explicitly, so the database never inherits a case-sensitive server default (a database’s collation is independent of the server’s). PostDeployment warns if it ever finds a case-sensitive database, since collation can’t be safely re-set after the fact.
  • Transient objects use COLLATE DATABASE_DEFAULT. tempdb (and msdb) follow the server collation, not the database’s — so a #temp char column, or a comparison against a job-catalog string, can still collide. Pinning those to DATABASE_DEFAULT resolves them to the RR database collation; it’s a no-op on a CI server.

Identifier case — match the defined case

Reference every table and column at its canonical (defined) case, not lowercase. A customer database is created case-insensitive, so case is cosmetic there — but on a case-sensitive server a lowercase reference to a mixed-case object fails with Invalid object name. Matching a reference to the defined case is a text-only change with no schema impact, so it is always safe to do.

  • JD Edwards tables stay UPPERCASE (F4111, F0911, F43121) — that is how they read, and lowercasing them would be both a regression and a needless rename.
  • Never rename an existing table or column just to change its case. A rename is a schema migration (it ripples into indexes, views, the SSIS column maps, and the Services jar), so it is out of scope for routine edits. New objects are written in canonical case from the start.

Formatting

For new or edited objects: UPPERCASE keywords; identifiers at their defined case; schema-qualified names (dbo.); explicit column lists (no SELECT * in a shipped object or view); one major clause per line; consistent indentation. Applied going forward, not as a mass reformat of existing files.

Annotate the object

When an object does something for case- or collation-safety that would otherwise look like an unexplained workaround, leave a short comment saying what it is doing and why — so the next DBA understands the intent instead of “cleaning it up” and reintroducing the bug.
