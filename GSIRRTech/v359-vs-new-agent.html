Overview

This doc answers the four questions the team keeps asking when the conversation turns to the green-field data-services agent:

  1. What changed at the Agent level vs the Data Services level?
  2. Were any existing endpoints changed in a breaking way?
  3. Which v359 endpoints are absorbed by the new agent today, which are net-new, and which are still missing?
  4. Will the new agent support existing v359 customers?

Pair this doc with:

  • Deploy architecture — the three-component install model + the Actuator contract a new Services jar plugs into. (RapidReconciler-Agent/docs/deploy-architecture.md)
  • API.md — full v359 controller catalog (the “before” picture). (RapidReconciler-Agent/docs/API.md)
  • Gotchas — field-name traps + the two ValidationLight sources that have the same shape and different semantics. (RapidReconciler-Agent/docs/gotchas.md)
TL;DR
  • V7’s agent layer is unchanged; V8 ships its own broker. The new Services jar is a from-scratch rebuild of the per-DB HTTP process that V8 talks to. V7 installs keep their rr-valc-agent.jar broker and the central VALC SPA as they are. A V8 install runs the V8 broker, built from the existing broker source in RapidReconciler-Broker (version 2.1.0) and fitted to the V8 Services jar’s launch contract. See § 1a.
  • No existing endpoint has been changed in a breaking way. Three endpoints have shipped additive changes (/inventory/as-of, /inventory/audit-detail, /poll); each is backwards compatible with v359 callers.
  • V8’s entire boot path is absorbed. The dev box can shut v359 entirely. The legacy AngularJS SPA still hits v359 on its own host because it exercises endpoints (In Transit, PO Receipts, Roll Forward, Admin) that the new agent doesn’t expose yet.
  • Customer compatibility is gated on closing that gap. Today the new agent is V8-shaped, not v359-feature-complete. Production-blessed release + legacy-SPA smoke test are both still ahead.

1. Agent level vs Data Services level

Every RapidReconciler install has three independently-versioned components (see deploy-architecture.md):

ComponentWhat it isWhere it runsChanged?
Valc Central SPA + server. staging-valcspa.cloudapp.net / rr-valc-spa.cloudapp.net No. RapidReconciler-Valc is VALC 2.0, the control plane + JMS server V8 installs connect to.
Agent rr-valc-agent.jar — the JMS message broker client. Owns file streaming, SHA1 verification, Services instance start/stop, self-update, Derby DB at db\. Each customer host, under the WinSW wrapper. V7: C:\Program Files\Rapid Reconciler, service rr-valc-agent. V8: C:\Program Files\Rapid Reconciler V8, service rr-v8-agent. V7: no. V8: yes — the V8 broker, built in RapidReconciler-Broker from the existing broker source (§ 1a).
Services Per-DB HTTP jar at files\<n>\ — the one V8 calls. Spawned by Agent, one process per DB. Yes. This is the entire green-field rewrite. New package coral.rapidreconciler.client.services.* in the agent repo’s src/.

The Actuator contract in specs/actuator-deploy-integration.md (/health and /info on a management port, POST /shutdown) is what the existing broker expects. The V8 Services jar serves none of that: GET /health on its service port answers {"status":"ok","agent":"client-services","version":"8.0.x"}, and it has no management port. The V8 broker probes that endpoint instead and stops a Services process by its PID (§ 1a).

On a V8 install the deploy flow is: VALC 2.0 publishes the desired state (every active database, each on its own pinned Services release; only a deploy changes a pin, VLC-131), the broker requests the file, verifies its SHA-1, starts one Services process per database, and reports health in its heartbeat. VALC 2.0 closes the deploy from those heartbeats: SUCCEEDED when the instance reports up and, for Services 8.0.41 and later, reports the target version in its facts; FAILED when it reports down with an error, except the broker’s “file does not exist” while it is still fetching the jar, which keeps the deploy waiting because the broker retries the start once a minute; TIMED_OUT after 15 minutes. Each deploy row records the operator who started it (client_deploys.triggered_by).

From broker 2.1.2 with Services 8.0.41, the heartbeat also carries each instance’s install facts (host, OS, Java, free disk, memory, SQL engine, build, compatibility level, collations, database size and the install checks) every five minutes. The broker reads them from the Services process on the same server, and VALC 2.0 files them only against that customer’s own databases. Every heartbeat now also records the broker as connected, and the broker reports its own version after it connects. Before this, a broker-run install reported none of these, and VALC 2.0 showed a connected broker as never connected.

Every heartbeat has always carried each instance’s refresh-job status (v359’s dbSystemStatus and dbSystemStatusMsg). v359 and brokers up to 2.4.1 read it from the view v_diagnostic5_job_status; broker 2.4.2 reads dbo.usp8_job_status (DAC-85), the same procedure the Services’ own /poll reads since 8.0.43 (DAC-83). The view needs msdb db_datareader, which V8 installs no longer grant (DAC-84); the procedure needs only SQLAgentReaderRole. If the read fails, the broker reports its older log-based status and logs one warning per database. VALC 2.0 stored it and ignored it until 2026-10-02 (VLC-120): a broker-run Clients card now shows the same Job Status (Successful, In Progress, Failed, with “Data as of”) a VALC-run one does. The broker’s status cannot say Cancelled; v359 reports that as unknown, and VALC shows it as not reported. The go-live check “Company data has loaded” reads the company list on the customer’s box through the broker (2.4.0+), at most once a minute per database.

1a. The V8 broker

V8 ships its own broker, built from the existing broker source. The source was copied without history into RapidReconciler-Broker (a GSI GitHub repo) on 2026-09-26, and it is used only by the V8 installer. V7 installs keep the broker they have. A V7 customer testing V8 runs both on one server: each has its own folder, Windows service and runtime.

AreaV8 broker (2.4.4)
InstallThe V8 installer puts it in C:\Program Files\Rapid Reconciler V8 as service rr-v8-agent (“Rapid Reconciler 8 Agent”), on a bundled JRE 21. The file names stay rr-valc-agent.* because the broker’s self-update and log upload use them. The installer refuses to write into a folder or service another product owns.
RuntimeJava 8 bytecode, built and tested on JDK 8 and 21. It runs on the bundled JRE 21 and starts every Services jar on that same runtime.
IdentityConnects with the install bundle’s valc.client-id and valc.secret (rr-common AgentConnection, unchanged since 1.7.0; the broker ships rr-common 1.8.0). VALC 2.0 verifies the secret; the external IP is telemetry only, and an agent that presents no valc.client-id is refused (VLC-127); from 2.3.0 the broker does not dial without one. From 2.3.0 the same id and secret are also the JMS username and password on every connection to VALC’s Artemis, and VALC checks them there (VLC-128). A broker older than 2.3.0 presents none and is refused before it reaches any queue. A connected broker can use only its own queues: not another customer’s, not the handshake queue’s incoming messages, and not the management address. Regenerating the installer rotates the secret, closes the broker’s JMS connections and ends the live session: VALC drops that broker’s heartbeats and publishes nothing to it until it reconnects with the new secret (VLC-122).
TLS to VALCTrusts VALC 2.0’s JMS acceptor with the truststore shipped in the install bundle. No client certificate: VALC 2.0’s acceptor does not ask for one. valc.jms.http really turns TLS off.
Database passwordsHanded to each Services process in its environment (SPRING_DATASOURCE_PASSWORD, SPRING_DS_JOB_PASSWORD), never on the command line, and never logged.
Launch contractThe same arguments VALC 2.0’s own spawn uses: --server.port, --agent.database-uuid (the database’s identity, which scopes each request) and --agent.database-name, --agent.jwt.public-key-path (VALC 2.0’s JWT public key, shipped in the install bundle as valc-jwt-public.pem), an mssql-jdbc datasource URL, and TLS off unless VALC marks the instance https. It refuses to start a Services jar when the key file is missing.
Heap-Xmx<N>m from client_databases.max_memory_mb (megabytes end to end).
Crash filesFrom 2.4.3 a Services JVM that crashes writes its crash log to logs\hs_err_pid<pid>.log (compiler replay data to logs\replay_pid<pid>.log) and no minidump. Older brokers let both land in the install folder, and nothing removed them. The broker deletes crash files older than 14 days in logs\ and the install folder. When a Services JVM dies before it is healthy, the broker reads that crash log and sends the reason, how often that database’s Services crashed in the last 24 hours, and the log’s path as the instance’s error in the heartbeat. VALC 2.0 shows it on the database’s row on the Clients page and in the Support Center’s offline line. Before this the heartbeat said only “exited with code 1” (VLC-150).
Restart backoffFrom 2.4.4, when a Services JVM keeps failing to start, the broker waits longer between attempts: the first failure is retried on the next pass, then after 2, 4 and 8 minutes, and then every 15 minutes. Only a start that launched a JVM counts; a database that cannot be reached or a jar still being fetched is retried every minute. A healthy start, a deploy or a changed setting from VALC 2.0 resets it, and the broker never gives up on its own. While it waits, the instance’s error in the heartbeat says when it tries again. Up to 2.4.3 it relaunched every ~70 seconds: 25 times in 30 minutes on 2026-10-01 (VLC-160).
Database loginThe desired state carries the SAME SQL login VALC 2.0’s own spawn uses: user and password from the Topology row first, the database row’s own columns only when Topology is blank; host from the database row first. They used to differ, and on the dev box one database’s row login was a stale one that SQL Server refused (VLC-123).
Job connectionAn unset job connection defaults to the database’s own (address, port, user, password, and job database name = database name), as v359’s VALC did. Up to 2.4.0 the broker kept the job database name unique per instance (a Derby unique index, which also treats two NULLs as equal), so VALC 2.0 sending none stopped a broker from running more than one database (VLC-123). From 2.4.1 two databases may share a job database: the limit is gone, and the broker drops the index an older version built when it starts (VLC-126).
Applying a publishFrom 2.4.1 each database in a publish is applied on its own. One the broker cannot store no longer stops the rest, the stop of databases VALC no longer lists, or the company licences; it is reported down in the heartbeat under its own id, with the reason, and any password in that reason is masked. A database whose new settings did not apply keeps running on its previous ones. Up to 2.4.0 one failure dropped the whole publish, and the reason stayed in the broker’s log on the customer’s server (VLC-126).
VALC commandsSystem Status, Reset, Import JDE and deploy SQL arrive as ServicesCommandRequest (2.2.0+, rr-common 1.8.0), and the two company reads from 2.4.0 (rr-common 1.9.0); the broker calls the matching loopback Services endpoint off its JMS thread and answers ServicesCommandResponse. See §3a.
Health + stopGET /health on the service port, up on ok or UP, version read from the same body. It never starts a second copy over a live one, and stops a child by PID (destroy, wait 10 s, force).
Self-updateStops only its own Services children, then exits so WinSW restarts it. It never kills other Java processes on the box.
check-ipCalls VALC 2.0’s GET /check-ip, with 5-second timeouts. A blank setting skips the lookup, and with a client id the broker connects without it.
ReleaseA pushed v2.x.y tag builds rr-valc-agent-<version>.jar onto a GitHub Release; the V8 installer’s -BrokerJar takes that file.

VALC 2.0 side, built alongside it:

  • The customer’s broker always runs their RR Services. Every application server is broker-run; there is no operator switch (owner ruling 2026-09-27; V84 made new servers broker-run, V88 moved the rest). VALC 2.0 does not start, stop or probe those Services itself, and reads their state from the broker’s heartbeat.
  • Publish on (re)connect, to live connections only (a heartbeat in the last 90 seconds). VALC 2.0 refuses to publish a list shorter than the client’s active databases, because an empty list tells the broker to stop everything.
  • Deploy completion from heartbeats (SUCCEEDED / FAILED / TIMED_OUT), above.
  • Deploy SQL always goes through the broker for a broker-run database (VLC-125, 2026-10-02): the ad-hoc script, the SSIS configuration and cleanup steps, the JDE line-type merge and the module-entitlement sync. They used to run sqlcmd from VALC 2.0’s own server by default, which cannot reach a customer’s SQL Server. The Services run a script as one batch, so a script with GO lines is refused with a sentence and nothing runs.
  • A refused broker is shown, not just logged (VLC-130, 2026-10-02). Every refusal, at the JMS connection (no identity, unknown client id, wrong secret, a queue it does not own) or at the handshake, is recorded with its reason, time, count and source address, and the client’s Agent reachable row on the Agent Installer tab shows the newest one, with what to do, until the broker connects. No secret is recorded.
  • GET /check-ip, which returns only the caller’s own address.
  • The install bundle carries the identity, VALC 2.0’s JMS host and port, the check-ip URL, a per-bundle truststore, the JWT public key, and the Services certificate bootstrap password. The installer is one generic setup.exe; from installer 8.0.5 VALC writes these files onto a copy of it and signs that copy, so the customer downloads one file (older installers get a zip and read them from their own folder). It asks for no password: it generates the keystore password and moves the bootstrap password into the V8 secrets file. v359 needed no prompt because its Services jar carried the certificate password in plain text.

The end-to-end rehearsal ran on 2026-09-29 (a throwaway client, installer 8.0.2 then 8.0.5), and on 2026-09-30 the GSI dev server itself moved to its broker: three databases under rr-v8-agent on broker 2.2.0, with System Status answered through the broker.

2. Endpoint changes — additive only

The migration policy (feedback_v8_test_agent_default) is: preserve v359’s wire contract so V8 can flip a routing-table entry per area without changing client code. Concretely:

  • Request DTO field names match v359’s Jackson bindings (camelCase first-letter-lowercase; type not docType on transactions/details; daily not period on as-of).
  • Response field names match v359’s view-aliased column shapes.
  • The reconciliationFilter two-shape split (Item-wrapped on /reconciliation-filtered, bare-string arrays everywhere else) is preserved per API.md § Reconciliation filter shapes.

Three additive changes have shipped on existing endpoints, all backwards-compatible:

EndpointPRChangeCompatibility
POST /inventory/as-of Agent#23 New optional columns: List<String> body field for wire-level column projection. Omit it → full row. Old clients ignore the field; Spring binds it as null.
POST /inventory/audit-detail Agent#31 Response gains five additional arrays (accountSummary, accountDescriptions, unpostedBatchesUi, unpostedCardexUi, manualJournalEntries) alongside the existing reconcilingItems + perpetual. Jackson skips unknown response fields on the client; old clients see no change.
GET /poll Agent#32 Optional query params ?updating=&recalculating=&timeoutMs= enable v359-style long-poll. No params → classic short-poll (unchanged). Mini-VALC’s /health probe and any other no-param caller hit the unchanged short-poll path.

No existing endpoint has been renamed, removed, or had its DTO shape narrowed. The endpoint name typo on POST /inventory/rollIItem (double-I) is preserved verbatim — matches the bytecode.

The new agent runs the same Reset_RapidReconciler_Database @ResetLevel (M = minimal / P = partial) over a loopback HTTP endpoint, and VALC’s Databases-tab reset calls it.

How VALC reaches these on a customer’s box (VLC-120, broker 2.2.0). They are loopback-only, so VALC can call them directly only for a Services jar it runs on its own box. For a database the customer’s broker runs, VALC sends a ServicesCommandRequest (rr-common 1.8.0) naming one of four commands (System Status, Reset, Import JDE, deploy SQL) and the database’s uuid. The broker calls the matching endpoint on its own loopback and returns Services’ answer, status and bytes unchanged, as a ServicesCommandResponse with the same request id. The broker takes a command name, never a path, so it can reach only those endpoints. A broker older than 2.2.0 does not know the message; VALC checks the version the broker reports and refuses with a sentence instead of sending.

Broker 2.4.0 (rr-common 1.9.0, 2026-10-01) adds two read-only commands: the company reads /admin/companies/all and /admin/companies/all-with-unlicensed. Before them VALC refused both for a broker-run database, so the Deployment Center’s Bootstrap and Licensing panel stayed empty for every real customer. rr-common gained constants only, so the message’s fields and serial shape are unchanged. VALC gates these two on 2.4.0: a 2.2 or 2.3 broker is told to upgrade from the Deployment Center’s Upgrades tab, and the other four commands keep their 2.2.0 gate.

4. Auth surface

The v359 Services jar is a token verifier only. Login and change-password live entirely on the Azure VALC SPA (staging-valcspa.cloudapp.net / rr-valc-spa.cloudapp.net). There is no LoginController, AuthController, or PasswordController in either v359 or the new agent — both expect a pre-issued JWT in the Authorization: Bearer header.

Verification difference (security upgrade in the new stack). The V7 TokenService.parseToken calls JwtParser.isSigned(token) (a structural check only) then Jackson-deserializes the payload directly — the RSA signature is never actually verified against the public key. The new agent and VALC 2.0 both use modern jjwt 0.12 parseSignedClaims(), which DOES verify.

Cutover implication: the new agent will reject any malformed-but-structurally-valid tokens that quietly worked in production. Pre-flight a real customer token before a customer cutover. Full detail in RapidReconciler-Agent/docs/gotchas.md § Signature verification difference.

When VALC 2.0 takes over as the auth target it must mirror Azure VALC’s wire shape exactly:

EndpointOwner todayOwner after VALC 2.0 cutoverWire shape

POST /resource/client/change-passwordAzure SPA UI (out of band)VALC 2.0Net-new in the V8 context; spec TBD

V7’s LoginClaims.ServicesInstanceVO emits all 12 db-level fields. V7’s Services jar reads only the first 7 (ip,k,n,i,t,p,a) and Jackson-drops the rest; V7’s SPA reads the permission flags for UI gating. Every short key is a @JsonProperty annotation on the Java class — do not invent keys by guessing from the long names.

4a. Known token-shape divergence (V7 vs VALC 2.0)

The real divergence is not between v359 and the new agent — the fields exist in V7 tokens and the new agent reads them correctly. It is between V7’s and VALC 2.0’s minted shapes, which the new agent can’t serve both of. Open items:

5. Will the new agent support existing v359 customers?

Mechanically, through a V8 install, not through the V7 broker. A V7 broker starts Services on its bundled Java 8 runtime, and the V8 Services jar is Java 21 bytecode (its launcher alone is Java 17), so a V8 Services jar pushed to a V7 box cannot start (measured 2026-09-26). An existing customer moves to V8 with the V8 installer: it lays down the V8 broker, a JRE 21 and the VALC 2.0 install bundle in their own folder beside V7, and V7 keeps running until the customer is done with it.

Functionally, not yet. Four caveats block a real customer cutover today:

  1. Endpoint coverage is V8-shaped. The table above lists ~15 endpoint groups the new agent doesn’t expose. A customer whose deployed AngularJS SPA exercises In Transit, PO Receipts, Roll Forward, the daily-probe GET, PDF downloads, or any Admin module screen would see those screens break. The legacy SPA hasn’t been smoke-tested against the new agent — it currently runs against v359 on its own host (staging-rr-spa.azurewebsites.net / rapidreconciler.getgsi.com).
  2. V7 vs VALC 2.0 token-shape divergence (see § 4a). The new agent today is VALC-2.0-native — it reads top-level sub for username (which V7 tokens lack) and has no extraction path for dbs[i].t (in-transit companies) or dbs[i].p (PO Receipts companies). Real legacy-VALC-issued tokens hit the new agent with a null username and no In Transit / PO Receipts scoping. Resolution: pick one canonical token shape (most likely VALC 2.0’s) and either retire legacy VALC before deploying the new agent, or have the new agent defensively read both shapes.
  3. No production release has been cut. The new code currently runs only on the dev box (localhost:34537 / rrtest-rrsqltest.getgsi.com:34537). The repo’s main branch hasn’t been tagged v360 or otherwise blessed for deploy. The artifact in RapidReconciler-Agent/artifacts/v359/ is still the production reference.
  4. Engine floor SQL 2019; compatibility level pinned at 140. Two different requirements. The supported engine is SQL Server 2019 or newer; separately, the V8 install and every upgrade run ALTER DATABASE … SET COMPATIBILITY_LEVEL = 140 so the optimizer behaves identically whatever engine the customer bought (per feedback_sql_compat_floor and RRV8/WORKFLOW.md). Every SQL the new agent issues must clear compat 140 — the forbidden constructs are SQL 2022 features, above the pinned level, not above the engine floor; the dev DB sits at 140 to catch regressions early.

5a. Cutover preconditions

In rough order, a customer-ready cutover would need:

  1. Close the legacy-SPA coverage gap above (or sunset the legacy SPA in favor of V8 for the affected modules).
  2. Fix the JWT claim-shape divergence (caveat 2 above). Cheap, and unblocks correct behavior on every existing customer login.
  3. Tag a release on main and pin the corresponding artifacts/v360/ directory.
  4. Validate the V8 broker + JMS plumbing end-to-end against VALC 2.0 (scripts/rehearse-local.ps1 in RapidReconciler-Broker is prepared, not yet run), then on a real V8 install.
  5. Pilot on one internal install / one consenting customer with a rollback plan to v359.

None of these are blocked today — they’re just queued.

6. Agent updates and clean installs

No — agent-layer changes don’t require a clean install. In-place updates via JMS are the whole point of the architecture.

The mechanism is SelfUpdateMessage in rr-common:

FieldTypePurpose
lastAgentVersionStringThe target version (e.g. 1.6.21) — lands in client_deploys.target_version_string and surfaces in the dashboard’s Agent Version column.
lastAgentVersionIdlongfile_versions.id — the artifact catalog row VALC will stream from.
lastAgentVersionSha1hexString40-char SHA1; the agent verifies the streamed bytes against this before swapping the jar.

Deploy flow for an agent update:

  1. Admin uploads a new rr-valc-agent.jar into VALC → row in file_versions with component = 'agent'.
  2. VALC publishes SelfUpdateMessage to the agent’s receiver queue.
  3. Agent requests the bytes (SendFileMessage); VALC streams them (FileContentMessage).
  4. Agent verifies SHA1 against lastAgentVersionSha1hex.
  5. Agent swaps the jar on disk and exits. WinSW respawns it automatically.
  6. New agent jar reconnects via AgentConnection; subsequent dashboards reflect the new version through client_deploys.target_version_string.

This is the same flow Services jars use for redeploy — the only difference is component = 'agent' on the file_versions row vs component = 'services'.

On a V8 install (VLC-132): VALC 2.0 sent SelfUpdateMessage from the Deployment Center’s Upgrades tab, Broker band, and only when the broker has a live heartbeat, has reported its version, and the release is strictly newer. Since VLC-144 (broker 2.5.0) that band is the Agent band (§ 6b), and the jar push is used only to bring a broker older than 2.5.0 to one that can run an installer. The broker would take a downgrade as readily as an upgrade (it compares versions by plain inequality), so that guard is VALC’s. Broker releases come from RapidReconciler-Broker as component = 'broker', and VALC refuses a jar whose manifest version is not its tag’s. The V8 broker stops only the Services processes it started (by process handle, or by recorded PID with a matching start time) and then exits, and WinSW’s restart applies the new jar. It never kills other Java processes, so VALC and a V7 agent on the same box are unaffected. VALC records each upgrade in broker_upgrades: SUCCEEDED when the broker reconnects on the new version, FAILED when it reconnects on the old one after taking the jar (the rr-valc-agent.copies replacement did not apply), TIMED_OUT after 30 minutes. There is no rollback on the broker: a jar that will not start leaves WinSW restarting it, and the box needs the installer.

Measured on the dev server: WinSW 3.0.0-alpha.11 applies .copies. broker_upgrades 1 to 5 (2.2.0 to 2.4.3, 2026-09-30 to 2026-10-02) all SUCCEEDED, the wrapper log reading Handling copy: ...\files\<id> > ...\rr-valc-agent.jar before it starts the new jar.

The dashboard’s “Agent Version” column doesn’t ask the agent its version. Agents don’t self-report. VALC remembers what it pushed via client_deploys.target_version_string, and that’s what surfaces.

6a. When a clean install IS required

Exceptions, not the norm. Anything in the jar itself flows through SelfUpdateMessage; anything outside the jar needs manual intervention.

TriggerWhy self-update can’t cover itMitigation
JMS wire-format break If a change to rr-common removes a field the running agent reads, the old agent can’t deserialize VALC’s messages after VALC updates — including the SelfUpdateMessage that would have fixed it. SelfUpdateMessage itself is small and stable, but other messages exchanged with a not-yet-updated agent could break. Roll rr-common changes additively (new fields default to null on old readers; never remove or rename). Same policy V8 follows for endpoint shapes — see § 2.
WinSW wrapper config change If the .xml next to the service registration changes (JVM args, working dir, service name, log paths), self-update only swaps the jar — not the wrapper. V8, broker 2.5.0+: an installer release carrying the new .xml, sent from the Agent band (§ 6b); setup refreshes the service from it. V7: redeploy the wrapper and re-register the Windows service.
JDK floor change If the new agent jar requires a newer JDK than what’s on the customer host, the JVM rejects the bytecode before the new jar gets a chance to run. Install the new JDK on the customer host first, then push the jar. On a V8 install that runtime is the installer’s bundled JRE (Java 21 today), and the broker also spawns every Services jar on it, so a Services floor above 21 needs a new agent install first. With broker 2.5.0+ that install is sent remotely from the Agent band (§ 6b). build-installer.ps1 refuses a JRE that cannot load the Services jar.
First-time install on a new host No agent yet — nothing to self-update. Clean install via the installer.
Service registration corruption Edge case: the Windows service entry is broken (manual sc delete elsewhere, antivirus interference, etc.). sc commands to repair, or a reinstall to restore.

The rr-common JMS contract is the boundary to stay backward-compatible across. Treat it like a public API: add fields, don’t remove them.

Worked example — rr-common 1.7.0. AgentConnection (the bootstrap message every agent sends on connect) gained two fields, clientId and secret, appended after the original three. The serialVersionUID was deliberately left unchanged, so a pre-1.7.0 agent still deserializes VALC’s messages — the new fields simply arrive as null. This is the “add fields, don’t remove them” policy in practice: it gives each install a stable identity (verified by a hashed secret) that survives WAN-IP changes, without breaking the wire format for an older agent. The wire format is all it preserves: an agent whose fields arrive as null is refused, because VALC 2.0 no longer identifies anyone by external IP (VLC-127). The V8 broker (2.1.0) sends both fields from the install bundle; a V7 broker sends neither, so VALC 2.0 refuses it. In RapidReconciler-Broker every rr-common message class now declares its serialVersionUID, pinned to the value the 1.7.0 jar already had, and SerialShapeTest fails the build if a class’s UID or serialized field list changes.

Coral version2 (2026-06). Coral pushed a version2 branch across the legacy repos that repoints the central stack off Azure onto getgsi.com Linux/Docker hosts: the agent targets rrjms-dev.getgsi.com:8001 (was 443) and a single getgsi wildcard cert (PKCS12), server-side IP detection moved to X-Forwarded-For (behind a Linux LB), and a new getgsi JWT signing keypair ships in rr-valc. Crucially, rr-common is not in version2 — the JMS DTOs + JWT claim shape are unchanged, so everything in this doc still holds on the wire. The rr-valc-agent change is config/cert only; the customer-box install stays Windows/WinSW. The V8 broker packages none of those hosts or certificates as defaults: the VALC 2.0 install bundle supplies the JMS host, port and truststore.

6b. Upgrading the whole V8 agent from the installer (VLC-144)

No v359 analog: v359’s broker only ever replaced its own jar. On a V8 install the jar push leaves the bundled JRE, the WinSW wrapper and its .xml as first installed. From broker 2.5.0 (rr-common 1.10.0) VALC can send an installer release instead, and the box runs the installer’s own upgrade in place.

StepWhat happens
SendThe Deployment Center’s Upgrades tab, Agent band, starts a rollout of one installer over the chosen customers, five at a time. VALC sends AgentUpgradeMessage (installer file id, SHA-1, SHA-256, version, release file name).
Fetch and checkThe broker fetches the installer over the file channel (SendFileMessage / FileContentMessage), copies it to <install>\upgrade\, and refuses unless the copy’s SHA-256 equals the release’s .sha256 value VALC stored at import. It also refuses unless it runs from the folder the V8 installer recorded.
Hand overThe broker registers a one-shot task (SYSTEM, no trigger) and starts it, then reports HANDED_OVER. The task, not the broker, runs setup: setup stops the service, and WinSW’s stop ends the broker’s whole process tree.
Installrun-upgrade.ps1 runs setup /VERYSILENT /SUPPRESSMSGBOXES /NOCLOSEAPPLICATIONS. Run without an install bundle, setup keeps application.properties, so the box keeps its identity.
RecoverIf setup fails part-way, the script runs it once more. If the service is left stopped, the script starts it again, except after a failed config lock, where setup keeps it stopped on purpose.
ReportThe broker that runs next sends the script’s result (AgentUpgradeStatus RESULT) and, after every handshake, what the box runs: the installer DisplayVersion from its uninstall key, its JRE and broker.
JudgeVALC marks the box SUCCEEDED when it reports the target installer after the upgrade was sent and every database that was online is online again, within 10 minutes. Otherwise FAILED, or TIMED_OUT after 60 minutes, and the rollout pauses with the reason. Customers not yet started stay queued until someone resumes it.

Never backwards. A reinstall sets the broker to the one the installer packages, so VALC refuses an installer whose broker is older than the box’s, and an installer older than the box’s. A box with no heartbeat is skipped: someone on that box has to run the installer. A broker older than 2.5.0 is first brought to 2.5.0 by the jar push above, then sent the installer.

Measured on the dev server before it was built (2026-10-02, the upgrade script run as SYSTEM from a task, elevated): installer 8.0.6 to 8.0.8 succeeded in 40 s with the same identity, and the Services were back about 2 minutes after the service stopped. With the last JRE file held open, setup exited 5 and the script brought the agent back. Setup’s rollback does not restore files it already replaced (measured with a throwaway Inno installer): a part-way failure leaves a mixed install while the uninstall key keeps the OLD version. That is why the script retries once, and why VALC trusts what the box reports rather than the target.

Integrity: SHA-256 today. A publisher (Authenticode) check follows once GSI has a trusted code-signing certificate.
