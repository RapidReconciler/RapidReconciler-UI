Overview

RapidReconciler_Prod.dtsx is a single SSIS package that pulls the JD Edwards tables RapidReconciler reconciles (the cardex, the GL, item master/branch data, receipts, batch control, sales detail) out of the customer’s JDE database and into their RapidReconciler database. There is one package for every customer and every platform — the extract SQL is portable; only the JDE source driver and a handful of parameter values differ per install.

  • Source: the customer’s live JDE database (SQL Server, Oracle, or IBM i / DB2), read-only, via the JDESource connection.
  • Destination: the customer’s RapidReconciler database, via the RRLocal connection, as the rruser login.
  • Deployment: the SSISDB project deployment (catalog) model — folder RapidReconciler, project RapidReconciler-SSIS, package RapidReconciler_Prod.dtsx.
  • Orchestration: VALC builds a per-customer catalog environment, deploys the .ispac, and runs the package (full load, bootstrap, or a per-group preload) from the Deployment Center.

This spec describes intended behavior and the verified contract. When a value or shape matters (a JWT claim, a sign convention, a parameter type), the source of truth is the live .ispac read back from the catalog — the parameter table in §3 was pulled from SSISDB.catalog.object_parameters, not from memory.

1. Deployment model

The package ships as a project .ispac deployed to the SSISDB catalog. Per-customer configuration lives in a catalog environment (one set of variables per database), bound to the package parameters by an environment reference. This replaced an earlier package/msdb model + a SQL-Server config table; the catalog gives parameter typing, an execution history (catalog.executions / event_messages / executable_statistics), and the standard SSMS execution reports.

Catalog objectValue
FolderRapidReconciler
ProjectRapidReconciler-SSIS
PackageRapidReconciler_Prod.dtsx

Protection levelDontSaveSensitive — the package carries no credentials; passwords come from the environment at run time

Catalog mutations (deploy_project, create_execution, environment build) reject SQL authentication (Msg 27123) — they require a Windows principal. On a SQL 2019 engine there is no Entra option, so VALC (and the dev tooling) run catalog operations through a durable per-database SQL Agent job whose T-SQL step executes as the Agent’s Windows service account (a member of SSISDB ssis_admin). See §13.

The .ispac deploys to any engine at or above the SQL 2019 floor, by construction. Both the repo artifact and the copy VALC stages for deploy carry TargetServerVersion 140 (SQL 2017) and PackageFormatVersion 8 — measured 2026-08-22 by reading each manifest. An SSIS catalog accepts a project built for its own version or older, so a package targeted below the floor is the safe direction. This is the opposite of the dacpac defect fixed in DAC-65, where a Sql160 target made the artifact impossible to publish to a 2019 engine at all. Not yet measured: a catalog deploy and a real package execution on a 2019 engine. Deployability is settled; everything the package does once it runs is not.

The same package serves four operational shapes, selected by the parameters above:

5. Date & horizon logic

All date scoping derives from one lever, aaStartDateGr, plus the look-back windows. A single Compute Load Dates Execute SQL task (with qryLoadDates) computes every per-table date boundary up front, replacing what used to be six separate date tasks and seven query variables.

  • Full load reaches back to aaStartDateGr (the floor). F43121 seeds start−2yr; F42119 is normalized to the same horizon.
  • Steady load windows the net-change pulls by RefreshDays (inventory/GL, default −35) and RefreshDaysRNV (receipts, default −90).
  • JDE stores dates as Julian (CYYDDD); the data flows convert to date in a Derived Column. The single date lever feeds both the Julian and Gregorian forms the queries need.

Self-deriving horizon (planned VS pass). When the package runs outside VALC (a scheduled job, the install job), an env default could bind a stale static start date. The fix: an empty sentinel + Compute Load Dates derives MIN(rcompanies.PeriodCutoff) − 90 so a non-VALC run can’t bind a wrong floor. Spec: docs/plans/ssis-compute-load-dates-horizon.md.

6. Decimal self-derivation

JDE stores quantities and costs as scaled integers; the display scale is data-dictionary-driven and varies by customer. RapidReconciler must apply the customer’s scale or every amount is off by powers of ten.

The four Dec* parameters (DecExtCost, DecUnitCost, DecQty, DecQtyCX) are mined from the JDE data dictionary at run time — read from F9210.FRCDEC for the relevant data items — never asked of the customer. On a SQL-platform JDE, VALC mines them at deploy time and freezes them on the environment (with a drift guard); on a non-SQL JDE the in-package derivation applies. A Derived Column divides each raw integer by its scale (e.g. ILUNCS / DecUnitCost).

Every table falls into one of three load patterns. Knowing which a table uses tells you what the data flow looks like and where to make changes.

9. Net-change — the staging + MERGE refactor

The net-change flows used to detect changes inside SSIS with a blocking Sort + Merge Join + Conditional Split. The Sort fully buffers the windowed pull in memory and grows with the refresh window — the package’s memory hot spot. The refactor turns each net-change flow into a dumb pipe (JDE source → Derived Column for type/decimal conversion → FASTLOAD into a Staging_* table) followed by a single set-based T-SQL MERGE in a versioned stored proc. SQL Server does the big join with proper memory grants, tempdb, and indexes; SSIS comparison memory drops to zero, and a junior can read a named proc instead of a ten-component pipeline graph.

The F4111 cardex change problem (worth understanding)

Work-order and sales-order transactions are written to the cardex ahead of their batch creation — they sit in RR incomplete (ilicu = 0, no batch number) until R31802/R42800 cut the GL batch. RR must capture them incomplete or the roll-up to F41021 breaks. The old change detection re-pulled JDE rows WHERE ILICU >= max(our batch) — a gamble on batch-number monotonicity that misses a completion whose batch lands below the high-water number, and a full scan besides (no index leads on ILICU).

The refactor instead fetches each still-open row’s current JDE state by ILUKID (the clustered PK — the only seekable lever on F4111), with the watch-set self-derived: the batch-pending document types are learned from the customer’s posted GL (F0011 / order types under the work-order and sales batch types), so it never hard-codes a per-customer doc-type list. usp8_f4111_build_change_pull range-compresses the open ukids into the pull predicate; usp8_apply_f4111 MERGE-updates the matched rows. When a row completes, its ilicu flips and it drops out of the open set automatically — self-cleaning, no batch assumption.

Per-run change counts

Each usp8_apply_* proc writes a row to dbo.RSsisLoadLog (new + changed counts). See §12 — an Execute SQL task cannot surface a T-SQL PRINT to the catalog log, so the log table is the durable record.

Full design + per-table reverse-engineered parity contracts + the VS rewiring steps live in docs/plans/ssis-staging-merge-refactor.md.

10. Performance model

The full load is resource / I-O-bound, not scheduling-bound. Profiling (SSISDB executable_statistics) shows the critical path is Inventory → Orders with GL as a parallel ceiling. On a real client-scale source (~2.65M cardex rows) a clean full load runs ~6m37s end-to-end and a steady incremental ~1m48s; F4111 dominates the early phase and everything else overlaps it.

The big lever was logging, not concurrency. LOGGING_LEVEL = Basic (set per execution, §3 of the catalog model) is now used for every run. At Verbose, SSISDB writes several rows per pipeline buffer; on a multi-million-row load that write amplification dwarfs the data movement — it was the “why is this so much slower than the Import Wizard” symptom (a full load sitting at Verbose ran ~21 min). Nothing in the Load Progress UI reads the Verbose-only tables, so Basic costs nothing and is dramatically faster.

MaxConcurrentExecutables = -1 (auto-scale). The package ships with the property at -1 — SSIS scales to logical CPUs + 2 at run time, adapting per customer with no dial to pick. (The earlier per-run dial was driven by a property expression the runtime didn’t honor; the load runs ~CPUs+2 wide regardless and is critical-path / I/O bound, so forcing a number bought nothing.)

Intra-container parallelism was tested and reverted. Fanning out independent sub-flows inside GL/InvSupp/Orders regressed 107s → 130s — unthrottled it floods one SQL instance (~10 concurrent flows) into I/O contention. The original serial-within-container design is near the box’s sweet spot. The real memory/throughput win is the §9 staging+MERGE refactor (it removes the Sort), not concurrency.

Destination policy is normalized across all flows: FASTLOAD + TABLOCK + bounded commit (10k) + AutoAdjustBufferSize.

11. Configuration

All per-customer configuration is a catalog environment — one set of variables per RR database, bound to the §3 parameters. VALC builds it from the customer’s topology (the RRLocal host comes from the Topology, not an inline value) and the licensed modules. The two sensitive values (CM.JDESource.Password, CM.RRLocal.Password) are split out from the connection strings. The Dec* values are mined (§6), not entered.

There is no longer a SQL-Server config table or package configuration in the run path; the retired RRConfig / ConfigDB mechanism has been removed from the package entirely.

12. Load logging

dbo.RSsisLoadLog (log_time, table_name, new_rows, changed_rows, note) is written by every usp8_apply_* proc, one row per table per run.

Why a table and not the SSIS log: an SSIS Execute SQL task does not propagate a T-SQL PRINT to catalog.event_messages — verified at Verbose logging, the PRINT never appears. So the per-run counts the procs compute are durable only in RSsisLoadLog. VALC’s Load Progress card reads this table for the per-table “n new / m changed” line; per-container execution time comes from catalog.executable_statistics.

13. Deploy & run

Normal path: the Deployment Center builds the environment, deploys the .ispac, and runs the package. Because catalog operations need a Windows principal (§1), deploy and execute both go through a per-database SQL Agent job whose T-SQL step runs as the Agent service account (∈ SSISDB ssis_admin). The job is created/started over SQL auth by a sysadmin login; the step itself authenticates as Windows.

No-Entra catalog deploy (operations recipe)

  1. Stage the .ispac where the SQL engine service account can read it (OPENROWSET BULK reads as NT Service\MSSQLSERVER); grant read to that account + the Agent account.
  2. A helper proc in master runs catalog.create_folder (if needed) + catalog.deploy_project from the staged file.
  3. Create a one-shot SQL Agent job (TSQL step, @database_name=master) calling the helper; sp_start_job; poll sysjobactivity/sysjobhistory; verify catalog.projects.last_deployed_time advanced.
  4. Clean up the job + helper + staged file.

A stored proc is not a catalog object, so the usp8_* procs and the Staging_* tables deploy normally with the database dacpac — only the .ispac and executions need the Agent-job route.

Cutting a release (the .ispac artifact)

The package ships as a tagged release, parallel to the DB dacpac and Services jar flows. The artifact is the project .ispac.

  1. Rebuild + commit the .ispac. Unlike the dacpac (built on the self-hosted runner), release-ssis.yml publishes the committed repo-root .ispac — a hosted runner can’t build an SSIS project. So rebuild the .ispac in Visual Studio from the committed .dtsx and commit it before tagging.
  2. Tag ssis-v8.0-beta.N on main and push it; the ssis-v* prefix fires release-ssis.yml, which attaches the committed .ispac to a GitHub Release.
  3. Sync into VALC. The Deployment Center’s Sync from GitHub for the SSIS component (or POST /api/v1/file-versions/sync-from-github?component=ssis) pulls the .ispac into file_versions (component ssis), where it becomes the deployable build.

This is the release/version step; the deploy step above is per-customer. The DB dacpac (Database Spec §10) and Services jar (Services Documentation) follow the same tag → build → sync shape.
