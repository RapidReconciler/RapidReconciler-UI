Overview

The RapidReconciler-Agent repo ships Services jar releases on git tags. Despite the repo name, the produced artifact is the per-DB Services jar (client-services-X.Y.Z.jar) — the green-field rewrite of v359’s Services component, not the JMS Agent jar itself. Day-to-day work on Dev stays on 0.1.0-SNAPSHOT; when a chunk is release-worthy, a maintainer tags the commit, and the rest is automatic:

  • GitHub Actions rebuilds the jar with the tag’s version baked into @project.version@.
  • The built jar lands on the repo’s Releases page, ready to be uploaded into VALC.
  • Auto-generated release notes summarize commits since the previous tag.

Once a customer’s Services instance receives the new jar (via VALC’s deploy panel and SelfUpdateMessage), the dashboard’s Services Version column updates — the value lives in client_deploys.target_version_string, not in any Services self-report.

Scope: this doc covers the Services release flow. The broker jar (rr-valc-agent.jar, deploy slot component='agent') is released elsewhere, and which one a box runs depends on the install:

  • V7 installs run the existing broker. Its source lives outside our repos and it has no release flow on our side; the pinned reference is RapidReconciler-Agent/artifacts/v359/rr-valc-agent.jar.
  • V8 installs run the V8 broker, built from the existing broker source in RapidReconciler-Broker. That repo has its own tag-triggered release.yml: a pushed v2.x.y tag that matches broker/pom.xml builds and tests on Temurin 8 and attaches rr-valc-agent-<version>.jar, rr-common-<version>.jar and SHA256SUMS to a GitHub Release. The V8 installer’s build-installer.ps1 -BrokerJar takes that jar, so the broker reaches a customer inside the installer, not through VALC’s component='agent' slot.

See v359 vs new agent § 1 for the three-component breakdown and § 1a for the V8 broker.

If you haven’t yet, read v359 vs new agent § 6 for the self-update plumbing. This doc covers the release side; that one covers the deploy side.

1. Versioning convention

Semantic versioning, with a -SNAPSHOT default for the Dev branch.

WhereLooks likeWhat it means
Dev branch HEAD0.1.0-SNAPSHOTPermanent placeholder. Every merged PR ships under this version until a tag fires the Action. The Services jar’s /health endpoint reports this string verbatim.
Released tagv0.2.0Maven version becomes 0.2.0; the leading v is stripped by the Action. Jar baked in as 0.2.0; release published on GitHub.
Pre-release tagv0.2.0-rc1, v0.2.0-betaSame flow, but the GitHub Release is flagged Pre-release. Useful for letting a single customer pilot a build.

What goes in each component

  • Major (X.0.0): breaking changes to the JMS contract (rr-common) or a forced minimum JDK bump. Triggers customer-side action.
  • Minor (0.X.0): new endpoints, new fields on existing endpoints, additive Services jar features. Customers update by deploy; no install action required.
  • Patch (0.0.X): bug fixes, performance, no API surface change.

2. Cut a release

The whole dance is two actions inside Visual Studio: create a tag on the right commit, then push it. The Action takes care of the rest.

Prefer the command line? The CLI equivalent is two commands: git tag v0.2.0 && git push origin v0.2.0. The rest of this section walks through the Visual Studio UI.

Prefer Claude Code? Run /release agent (or /release valc) in any session. The command checks the repo state, proposes the next version, fast-forwards main to Dev, cuts the tag, watches the Action complete, and verifies the jar landed on the Release page. Pass an explicit version as the second argument (/release agent v0.2.1) to skip the proposal step.

The command file lives at ~/.claude/commands/release.md — user-scoped, so it works from any repo’s working directory. See § 7 if it isn’t available in a fresh session.

1

Open the repo in Visual Studio and switch to Dev

If the solution isn’t already open, use File → Open → Open from Git Repository or File → Recent Projects to load RapidReconciler-Agent.

Confirm the active branch in the bottom-right status bar — it should read Dev. If not, click the branch name and switch via the popup.

2

Confirm the working tree is clean

Open View → Git Changes (Ctrl+0,G). The Changes list should be empty — no pending stages, no unsaved files. Outgoing commits should be zero (Dev synced with origin).

Run tests in Test → Test Explorer or via the integrated terminal (View → Terminal, then mvn -B test). Don’t cut the tag if tests are red. The release workflow runs the suite again and refuses to publish on a red result (§ 3).

3

Pick the version

Open View → Git Repository (Ctrl+0,R) for the full history view. Scroll the local history graph or expand Tags in the left panel to see the previous release tag.

Review the commits between that tag and the current Dev HEAD — right-click the previous tag and choose Compare with Branch → Dev to see exactly what’s landed.

Decide major / minor / patch using the table in § 1.

4

Create the tag

In the Git Repository window, find the commit at the tip of Dev (top of the history graph). Right-click it and choose Create Tag.

In the dialog:

  • Name: v0.2.0 (always lead with v; the Action strips it).
  • Message: a short summary — this is the annotated tag’s message and shows up in git log. E.g. Services v0.2.0 — DMAAI overlay endpoints, audit-detail expansion.

Click Create. The tag now exists locally; it hasn’t been pushed yet.

5

Push the tag

Still in the Git Repository window, expand Tags in the left panel. The new v0.2.0 entry appears with a small “up-arrow” marker showing it’s local-only.

Right-click v0.2.0 and choose Push Tag. (Alternatively, Git → Push Tags from the menu bar pushes every unpushed tag at once — useful if you batched several.)

Pushing the tag is what triggers .github/workflows/release.yml on GitHub. This is the only externally-visible step.

6

Watch the Action

Visual Studio doesn’t surface GitHub Actions natively. Open the repo in a browser, go to Actions → Release, and watch the run.

Typical build: 1–2 minutes. When it finishes you’ll see a new entry under Releases with the jar attached and auto-generated release notes filled in.

Visual Studio 2022 only. Earlier VS versions had Team Explorer instead of the modern Git tooling described above. The steps differ; this doc assumes VS 2022.

3. What the Action does

The release workflow at .github/workflows/release.yml runs on every v* tag push, and on every merge to main that touches the Services source (through auto-release.yml). Step by step:

StepWhat it does
GatesThe gates run inside the release job, on the commit and in the build that is published. If any fails, no tag is pushed and nothing is published. The fail-closed checks refuse a jar that would skip JWT signature verification: three read the source before the build, and one reads the built jar's application.yml. The build step below runs the full test suite, and its summary lists the tests CI cannot run: the keystore tests need RR_CERT_BOOTSTRAP_PASSWORD and the SQL batch tests need RR_TEST_SQL_URL. Every pull request runs the same gates in its checks run, but GitHub cannot be set to block a merge on it for this private repository on its current plan. A red PR can still merge. Its jar just never publishes.
CheckoutPulls the tagged commit (not main / Dev HEAD).
Setup JDK 25Temurin distribution. The build runs on 25, but the Services jar is compiled for Java 21, which stays its runtime floor: on a V8 customer box the V8 broker launches it on the one Java 21 JRE the V8 installer bundles, the same runtime the broker itself runs on. Maven cache is restored from the previous run.
Derive versionStrips the leading v from refs/tags/v0.2.0 → 0.2.0. Stored as a step output.
Set Maven versionmvn versions:set -DnewVersion=0.2.0 -DgenerateBackupPoms=false — rewrites the <version> in pom.xml in place. Not committed; only used for this build.
Build and testmvn -B verify: the full test suite, then the jar. The jar that passed the tests is the jar that is published. A failed or unexplained skipped test stops the release here.
Check the broker requirementRefuses to publish a jar whose MANIFEST.MF has no valid RR-Min-Broker-Version: the oldest V8 broker the jar runs under, set by the pom property rr.min-broker-version (2.1.1 today, the first broker that passes the database uuid). VALC reads it at import and lists the release only for customers whose broker meets it. Raise the property in the same change that makes the jar depend on a newer broker.
Check the database requirementRefuses to publish a jar whose MANIFEST.MF has no valid RR-Min-Database-Version: the oldest RR database release the jar runs against, set by the pom property rr.min-database-version (8.0-beta.132 today, the release that created usp8_job_status and usp8_job_history). VALC reads it at import, lists only database releases at or above it beside this release on the Fleet Upgrades tab, and refuses to deploy the jar to an older database. Raise the property in the same change that makes the jar call a newer database object.
Publishsoftprops/action-gh-release@v2 opens a GitHub Release named after the tag, attaches target/client-services-0.2.0.jar, and auto-generates release notes from PRs merged since the last tag.

The Action doesn’t commit the version bump back to the repo — that’s deliberate. Dev branch HEAD stays on -SNAPSHOT, no chore commits cluttering history.

4. After the release

The jar on the GitHub Release page isn’t the Services install path on its own — it has to land in VALC’s artifact catalog (the file_versions table) before any of the deploy paths can reach a Services instance.

Two deploy paths exist, both feeding off the same file_versions row:

  • Production deploy (V7 installs) — JMS-based. Goes through the central VALC SPA and the customer’s existing rr-valc-agent.jar. The path V7 customers use today. See § 4a.
  • V8 broker deploy — JMS-based, from VALC 2.0 to the V8 broker on a V8 install. This is the path for every V8 server. See § 4c.

Every application server’s RR Services run by reads Customer’s broker, read-only (owner ruling 2026-09-27; the dev server moved on 2026-09-30). The third path, an internal HTTP-push deploy to a Services process VALC 2.0 ran itself, was removed on October 2, 2026 (§ 4b).

Customer deploys are not automatic on every release. Releasing publishes the jar; deploying pushes it. This split is intentional — gives you a chance to pilot a release on one or two clients before fanout, regardless of which path you use.

4a. Production deploy (JMS via central VALC)

The mechanism real customers receive updates through. The customer’s legacy Agent jar is the receiver; VALC 2.0 isn’t in the picture at all.

  1. Open the new GitHub Release; download the attached client-services-X.Y.Z.jar.
  2. In production VALC, navigate to the artifact upload page; upload the jar with component = services. VALC records the SHA1, file size, and version string into file_versions.
  3. For each client you want to push the new version to: open Manage Deploy, select the new version, click Deploy. VALC publishes SelfUpdateMessage to the Agent’s queue, the Agent streams the jar to the per-DB Services slot per v359 vs new agent § 6, and a row appears in client_deploys with status = PENDING.
  4. Within a few seconds the deploy progresses through IN_TRANSFER → INSTALLING → SUCCEEDED. The VALC 2.0 dashboard’s Services Version column updates to the new value once the SUCCEEDED row lands (it’s pulled from client_deploys.target_version_string).

Watch the component slot. The artifact upload form asks for a component value. Services jars (this doc’s artifact) go into component='services'. The other slot, component='agent', is reserved for rr-valc-agent.jar — the legacy v359 JMS broker client. Uploading a Services jar into the agent slot will fail SHA1 verification on the customer side because the Agent’s HealthService expects a different Actuator contract than the Services jar exposes.

V7 and V8 installs each keep their own broker. A V7 install keeps its existing broker, and its Services updates keep arriving over the JMS path described above. A V8 install runs the V8 broker from the start, installed by the V8 installer into its own folder (C:\Program Files\Rapid Reconciler V8, service rr-v8-agent). A V7 customer testing V8 runs both side by side. Neither broker is delivered through this Services release flow: the V8 broker has its own release in RapidReconciler-Broker (see the Overview), and it ships inside the installer.

4b. Internal deploy (retired)

VALC 2.0 used to deploy a Services release to a Services process it had started itself, on its own server: it stopped that process, swapped the jar and started it again. That path was removed on October 2, 2026, together with the per-database Start, Stop and Restart controls it served.

VALC 2.0 no longer starts, stops or restarts any Services process. On every V8 server, the GSI dev server included, the customer’s broker runs them, so every Services deploy goes through § 4c. Testing an agent change on a dev database is a release plus a deploy, the same as for a customer.

4c. V8 broker deploy (JMS via VALC 2.0)

The path for a V8 install whose Services the customer’s broker runs. VALC 2.0 never starts, stops or probes those Services itself; it publishes what should run, and the broker does the rest.

  1. Import the jar into VALC 2.0’s file_versions with component='services'. The Deployment Center does this on its own each time it loads: it reads the GitHub releases for RapidReconciler-Agent, skips any already imported, and stores the new jars in the artifact store.
  2. Trigger the deploy one of two ways. For many databases, use the Deployment Center’s Fleet Upgrades tab, Services band, which skips a database already on the release. For one database, pick it in Step 1 and use its S (Services) step, which also re-deploys the version it already runs. Both follow the same rules. A customer with no heartbeat, or whose broker is older than the release’s RR-Min-Broker-Version, is refused with the reason (the Upgrades band lists it and it cannot be selected); upgrade its agent first, in the Agent band, from an installer whose broker is new enough (the Services dropdown lists only releases the picked installer’s broker can run; Agent Documentation § 6b). The same applies to a database older than the release’s RR-Min-Database-Version: deploy the database release first (the Fleet Upgrades tab’s Database dropdown lists only releases at or above that floor). The other direction holds too: a database release names the oldest Services release that still runs against it (RR-Min-Services-Version in its GitHub release, from db-release.properties in RapidReconciler-DB), so a Services deploy below what the database’s release needs is refused, and a database release is refused on a database whose Services is older than it needs (deploy Services first). The same Services rules apply to the operator API, POST /api/v1/clients/{id}/deploys. The one-database step answers sent with the client_deploys row id, then updates that row in place when the heartbeat decides it. The deploy sets that database’s pinned Services release (client_databases.services_file_version_id) to the version you picked, which may be older than the newest import. VALC 2.0 records a client_deploys row and publishes the desired state: every active database for the client, each on its own pin, so the client’s other databases do not move. It publishes only to a live connection (a heartbeat in the last 90 seconds) and refuses a list shorter than the client’s active databases, because an empty list tells the broker to stop everything.
  3. The broker fetches and starts. It requests the jar over JMS, checks the SHA-1, and starts one Services process per database on its bundled JRE 21, with the database password in the process environment and VALC 2.0’s JWT public key from the install bundle.
  4. VALC 2.0 closes the deploy from heartbeats: SUCCEEDED when the instance is up and reports the target version (the broker relays each Services 8.0.41+ jar’s own version every 5 minutes), FAILED when it reports the instance down with an error, except the broker’s “file does not exist” while it is still fetching the new jar, which keeps the deploy waiting (it retries the start once a minute), TIMED_OUT after 15 minutes, naming the version still running when it is the wrong one. A box or release that cannot report a version is judged on “up after delivery” alone.

VALC 2.0 also republishes the desired state on the first heartbeat after the broker (re)connects, so a broker that restarts picks up the current pins without a new deploy.

Only a deploy moves a broker-run box. Importing a newer jar changes nothing on a database that already has a pin. A database that has never been pinned (every one when VALC 2.0 first applies V89, and any database added later) is pinned on its next publish to the newest import, which is what it would have been sent anyway. To roll one back, deploy the prior version to it; the rollback in § 5 applies to broker-run boxes too.

Until V89 (2026-09-30) every publish pinned the newest import for every database, and a keep-alive publish goes out every 60 seconds, so a release tagged on GitHub reached every broker-run box within minutes of the catalog sync.

4d. The V8 UI release

The V8 app pages call Services, so the UI is a versioned component too. The knowledge base keeps publishing from main on GitHub Pages; the V8 surface is cut by tag in RapidReconciler-UI.

  1. Declare the floor. v8-release.properties at the repo root holds min-services-version: the oldest Services release every V8 page runs against. Raise it in the same PR as a UI change that needs an endpoint or field a newer Services release added. none is not accepted.
  2. Push a tag ui-vX.Y.Z. release-v8-ui.yml runs .github/scripts/package_v8_release.py, which starts from login.html, sso-landing.html and every RRV8/*.html and follows everything they load (scripts, stylesheets, fonts, images, and files a script fetches, such as the knowledge-base search index). It refuses to publish when the floor is missing or when a page loads a file that does not exist. check-v8-release.yml runs the same checks on every PR.
  3. The release carries three assets: rapidreconciler-v8-ui-X.Y.Z.zip, its .sha256, and rapidreconciler-v8-ui-X.Y.Z.manifest.json (version, commit, floor, every file with its SHA-256, and the links that stay on GitHub Pages). The body carries RR-Min-Services-Version: <v>, the same line shape the SSIS and database releases use.
  4. VALC 2.0 imports it as component='ui' on its five-minute catalog sweep. It refuses a release whose zip does not match its .sha256, or whose body and the manifest inside the zip disagree about the floor or do not state one. A manual upload of the zip reads the floor from that manifest.
  5. The floor is checked fleet-wide. One UI deployment serves every customer in an environment, each on its own Services. So a UI release is blocked while any active database there runs Services below its floor, or a Services version VALC cannot read. The Fleet Upgrades tab’s V8 UI dropdown shows the result and names each database that blocks it; the same check is GET /valc/deployment/ui-release-check?fileVersionId=<id>.

Nothing deploys the UI yet. The per-environment Web App that will serve a specific UI release instead of main is part of the QA environment build-out. Until then the release is cut, verified and checked, and GitHub Pages keeps serving main. When that deploy exists, a Services rollback below the deployed UI’s floor will be refused the same way.

4e. Promotion: Dev → QA → Prod by release train

Every VALC 2.0 imports every non-draft release. Floors stop only the combinations someone declared, so QA and Prod deploy only release trains: one version each of the agent installer, database, Services, SSIS and V8 UI that ran together on a dev database. Edward and Daren hold the sign-off, and one approval by either is enough (owner rulings, October 4 and 5, 2026).

Which rules a VALC applies comes from its valc.env, set on its own service command line. Only dev gets the Dev rules; qa gets QA; prod, and any other value including none, gets Prod.

  1. Propose, on the dev VALC. The Fleet Upgrades tab’s Release trains band lists each active database’s combination, read from VALC’s records: the installer the customer’s broker reported (it must install the broker the box reports), and the newest database, Services and SSIS deploys, each of which must be the newest attempt, SUCCEEDED, and match what the database reports. The V8 UI is the newest imported release whose Services floor the train’s Services meets, because nothing deploys the UI yet. Propose train is refused when any of that fails, when a declared floor between the five breaks in either direction, when the same five artifacts are already a train, or when no rollout order from the train QA or Prod runs avoids a combination the floors forbid. The train is published as a train-YYYYMMDD-HHMMSS pre-release in RapidReconciler-Valc with one line per component (version and SHA-1, plus SHA-256 for the installer and UI) and the order to roll it out in.
  2. Approve, on the QA VALC. The QA VALC imports train releases on its five-minute sweep, after the artifacts, and matches each component to its own catalog by SHA-1. A release approver clicks Approve for QA. The approval is written back to the train’s release as Approved-QA: <upn> <utc>; if that write fails, nothing is recorded. The QA VALC never believes an approval line it did not write.
  3. Approve, on the Prod VALC. The Prod VALC lists only trains carrying Approved-QA, with who approved it, and a release approver approves it for Prod.

On QA and Prod, a release that no train approved there carries is refused on every deploy path: the Fleet Upgrades bands, the one-database steps, a database install, an agent rollout, and the operator API POST /api/v1/clients/{id}/deploys. A rollout carrying several components must take them all from one train. The version dropdowns list only approved trains’ releases, and Step 1 adds a Release train picker that sets the five dropdowns and locks them. Dev behaves as before.

The release approver right is granted on the Operators page and only to a control-plane operator. A VALC starts with none; while it has none, any operator may grant the first, and after that only an approver grants or revokes it. Every proposal and approval is kept in VALC’s audit log (release_train_events) with who, when and the train’s contents.

Limits. Anyone with write access to RapidReconciler-Valc could add an Approved-QA line by hand. That lists the train in Prod; it does not deploy it, since a Prod approval is still required. A caller sending ids straight to the API could take one component from each of two approved trains; the floors still judge each step. The V8 UI’s fleet-wide check is shown with each train but does not block approval, because the train’s own Services rollout is what brings the fleet up to the UI’s floor. The QA and Prod legs have not run live yet: they wait for the QA environment.

5. Pre-releases & rollbacks

Pre-release

Tag with a suffix:

git tag v0.2.0-rc1
git push origin v0.2.0-rc1

The Action’s prerelease: field is set to contains(version, '-'), so any tag with a hyphen lands as a Pre-release on GitHub. Same artifact path; just a UI flag.

Rollback

Two options, depending on what went wrong:

  • Bad jar, deploys not yet sent: delete the GitHub Release (don’t delete the tag — future reference). Cut a new patch release (v0.2.1) with the fix.
  • Bad jar, already pushed to customers: redeploy the previous version. VALC’s artifact catalog keeps old versions; pick the prior one in Manage Deploy. The Agent streams the older jar to the Services slot and the per-DB instance restarts onto it.

Once a tag is pushed and the Action publishes, don’t delete the tag. Tags are part of the audit trail; reissuing a deleted tag at a different commit confuses everyone.

6. VALC 2.0 parallel

The VALC 2.0 repo (RapidReconciler-Valc) has the same release.yml workflow. Same tag flow, same Action behavior, same Release page. The only difference is the artifact filename: valc-X.Y.Z.jar instead of client-services-X.Y.Z.jar.

Different consumer model, though. VALC 2.0 isn’t a customer-deployed artifact — it’s the parallel dev-side broker + dashboard that replaces the central VALC SPA for local development. Its release jar doesn’t land in file_versions; it’s just downloaded and run directly via setup/run-mini-valc.ps1 or its successor. VALC 2.0’s version surfaces on its /actuator/info endpoint and in the dashboard sidebar footer once that’s wired through.

Target Linux/Docker deploy (VALC 2.0 control plane)

Beyond the local dev run above, the released valc-X.Y.Z.jar is headed for a GSI-operated Linux/Docker deployment — a real, isolated, authenticated control plane rather than a reachable dev box. This is the intended flow; the pieces are being built up in sequence (QA first, then production), so treat the steps below as the target, not as something already shipped end to end.

  1. Promote the released jar into a container image. The same valc-X.Y.Z.jar from the Release page is baked into a Docker image (JDK 25 base, non-root, a healthcheck on /actuator/health) — no rebuild per environment. The image, not the loose jar, is what gets deployed.
  2. Run the image on GSI-managed Linux. A compose stack (or equivalent manifest) brings up the VALC app container alongside its Postgres. QA and production run the identical image; only the injected configuration differs.
  3. Inject configuration and secrets from the environment. Per-environment values — Postgres credentials, the agent shared-secret, base URLs, and the allowed CORS origin — come from an application-qa.yml (or -production.yml) profile plus environment variables sourced from the host’s secret store. Nothing sensitive is committed to the repo or copied in as a config file.
  4. Terminate TLS in front of the web tier. A reverse proxy in the container stack (or server.ssl) fronts the 8080 web tier with HTTPS — required both because operator sign-in moves to Microsoft Entra ID single sign-on (its OAuth redirect needs HTTPS) and because a SOC-isolated control plane over plaintext isn’t defensible.
  5. Provision a clean Postgres. Flyway migrations run against an empty database on first boot; the environment comes up isolated, with no dev-seed clients or placeholder users.

QA proves the control plane; production then follows the same discipline — promote the same artifact, change only the externalized configuration.

Containerization is the control plane only. The Docker/Linux target here is for VALC 2.0 itself — the app, its Postgres, its config, secrets, and TLS. It does not change how the customer-side Services agent is installed: that continues to run as a Windows service (WinSW) on the customer’s application server, deployed by installer, and receives updates over the paths in § 4. Don’t read the VALC container work as a move to ship the customer agent in Docker — the two install models stay separate.

Tag-cutting cadence is independent of the Services repo — release each repo when its work is release-worthy.

7. Troubleshooting

SymptomCauseFix
Action ran, no jar attached to the Release The Maven build failed silently — check the Action’s logs for the Build jar step. Re-run the workflow once the underlying issue is fixed (you can’t fix it just by re-tagging; the same tag won’t re-trigger). Cut a new patch tag instead.
target/client-services-X.Y.Z.jar not found at the publish step The versions:set step didn’t apply, or the Spring Boot repackager produced a differently-named artifact. Confirm the pom uses ${project.version} in <finalName> (or omit finalName entirely). Re-tag with a new patch.
Tag pushed, no Action run Tag didn’t match the v* glob (e.g. 0.2.0 instead of v0.2.0). Push a new tag with the leading v.
Release notes empty or missing PR links generate_release_notes: true needs at least one merge between the previous tag and the new one. If no PRs landed between tags, the auto-generated notes will be terse. Edit the Release on GitHub to add narrative if needed.
Customer’s Services instance never picks up the new version The deploy step (after the release) wasn’t run, or SelfUpdateMessage hasn’t reached the customer’s Agent. Check client_deploys for a row with the target version; if absent, go to Manage Deploy and trigger the push. If the row exists but is stuck in PENDING / IN_TRANSFER, the customer’s Agent may be offline — check its JMS heartbeat in VALC’s clients list.
Services jar uploaded but customer health check fails immediately The jar was uploaded into the wrong artifact-catalog slot (component='agent' instead of component='services'). Re-upload into the correct slot. The Agent’s self-update path verifies Actuator endpoints specific to that component; a Services jar in the agent slot will fail the contract check.
/release command not available in Claude Code The command file is user-scoped at ~/.claude/commands/release.md; missing on a new machine, or the session started before the file was created. Confirm release.md exists under %USERPROFILE%\.claude\commands\. If missing, copy it from any machine that has it (it’s a single self-contained markdown file). Restart the Claude Code session to pick up newly-added commands.
