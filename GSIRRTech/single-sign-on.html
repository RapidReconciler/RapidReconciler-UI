Single Sign-On

SAML single sign-on lets a customer’s users sign in to RapidReconciler with their own corporate identity provider (e.g. Okta). It is a per-customer federation configured in the Deployment Center: hand the customer’s IdP admin our Service Provider details, load the metadata they return, choose the role new users receive, and enable. A user is created automatically on first sign-in — no password is ever stored or sent.

Overview

Most customers sign in to RapidReconciler with a username + password managed by VALC. Single sign-on (SSO) is an opt-in service for customers who want their people to sign in with their existing corporate identity provider instead — so access follows the customer’s own joiners/leavers process and password policy, and there is one fewer credential to manage.

SSO is implemented as SAML 2.0, where RapidReconciler is the Service Provider (SP) and the customer’s identity provider (Okta, Entra ID, Ping, etc.) is the Identity Provider (IdP). The first customer on this path is Kinross (Okta).

SSO complements email and password sign-in — it does not replace them. A few flows must reach people who can’t (yet) sign in, so they stay on email: the go-live hand-off + 7-day set-password link, password resets, and license/account notices. SSO covers day-to-day sign-in for a customer’s working users.

1. The sign-in flow

Once a customer is configured and enabled:

  1. The user goes to RapidReconciler and is sent to their IdP (or starts at their IdP’s app launcher).
  2. They authenticate with the customer’s IdP — their corporate login, MFA, the works. RapidReconciler never sees the password.
  3. The IdP posts a signed SAML assertion back to our Assertion Consumer Service (ACS) URL. The assertion carries the user’s identity (the NameID, an email).
  4. VALC verifies the assertion against the customer’s signing certificate, resolves (or auto-creates) the matching VALC user, and mints a normal V8 session token.
  5. The browser lands on the V8 Home page, signed in — exactly as if they’d used the password form.

The assertion is the proof of identity; from step 4 onward the user holds the same token a password login would have produced, so every downstream page and permission works identically.

2. Per-customer model

SSO config is stored per client (one row per SSO-enabled customer in client_sso, keyed by client_id), not as a single global setting. That matters because VALC is multi-tenant: only the customers who buy SSO are federated, each against their own IdP, and a misconfigured row for one customer can never affect another.

Each customer’s config carries a stable registration_id (used in the SAML URLs), the IdP details (entity ID, SSO URL, signing certificate), our SP details (entity ID, ACS URL), the email_domains that route to this IdP, and the default role new users receive.

3. Setup runbook

SSO is configured in the Deployment Center → SSO tab (also reachable from a customer’s Manage-Client card → “Single sign-on”). Pick the customer, then work the three bands:

Band 2 — hand the customer your SP details

The tab shows our Entity ID, Sign-on (ACS) URL, and a Download SP metadata button. Send the customer’s IdP admin the metadata file (or the values) so they can register RapidReconciler as a SAML application on their side.

Band 3 — load the IdP metadata they return

Paste the IdP metadata XML the customer exports (in Okta: Identity Provider metadata) and click Read metadata. VALC parses out the IdP entity ID, SSO URL, and signing certificate and fills the fields; review and adjust if needed. The parse runs entirely server-side via the JDK XML parser (no external calls), and is hardened against XML external-entity attacks.

Band 4 — choose the role and enable

Set the email domain(s) that route to this IdP, pick the default role new users get on first sign-in, tick Enable, and Save. VALC refuses to enable until the IdP entity ID, SSO URL, and signing certificate are all present — so a half-configured row can never go live.

The setup is a metadata exchange, not a switch — that’s why the customer card links to this tab rather than offering a one-click toggle. The customer’s IdP admin has to register us before sign-in can work.

4. Auto-provisioning & roles

SSO authenticates; it doesn’t pre-create accounts. The first time a user signs in through a customer’s IdP, VALC auto-provisions a VALC user for them:

  • Email = the NameID from the assertion; display name from the assertion (or the email’s local part).
  • A random, unusable password hash — these accounts never authenticate with a password.
  • The default role chosen in the SSO config (falls back to Read-Only if none is set — least privilege).
  • Access to every active database of that customer (company scope ALL), so the token carries a working data scope immediately.

On later sign-ins the existing user is reused. An admin can change the user’s role or scope afterward like any other account.

5. The token bridge

After a verified assertion, VALC mints the user’s normal V8 JWT — the same dbs[] scope and user block as a password login, with mustChangePassword forced off (there is no password to rotate). This is deliberately password-less.

The legacy rr-sso app bridged by posting the SSO email plus a hard-coded shared password to the login endpoint. That is not carried forward — it was a security liability. The new bridge mints the session directly from the verified assertion; no password is involved anywhere.

6. Hand-off to V8

VALC redirects the browser to a thin landing page in the V8 app (sso-landing.html) with the freshly-minted token in the URL fragment (the #… part). The fragment is never sent to a server and is dropped from the referrer, so the token doesn’t leak into access logs. The landing page stores the token exactly the way the normal login form does, scrubs it from the address bar, and lands the user on Home.

7. Status & roadmap

Shipped and usable today:

  • Per-customer config schema + the Deployment Center SSO tab.
  • SP-metadata generation and IdP-metadata parsing (the customer-facing round-trip).
  • The password-less auto-provision + token bridge, and the V8 hand-off landing.

Staged, pending one external dependency — the live assertion-consuming filter (the runtime that actually receives the SAML POST and verifies it) is now written, built on Spring Security’s SAML support. It sits behind an off-by-default build profile so the standard VALC build stays clean. The one thing it needs is the underlying SAML library (opensaml), which is published only to a vendor Maven repository the dev box can’t currently reach; the build resolves it automatically from any machine with access. Until that build ships, a customer’s IdP admin can complete their entire side of the setup against the metadata above; the final hop goes live the moment the library is in place.

8. Security notes

  • No shared secret. Trust is the IdP’s signing certificate on the assertion — per customer, never a shared password.
  • Tenant isolation. Each customer’s config and assertions resolve only to that customer’s users; one customer’s federation can’t reach another’s data.
  • Token in the fragment. The hand-off uses the URL fragment, not a query string, so the session token stays out of server logs and referrers; the landing page clears it from history.
  • Least privilege by default. Auto-provisioned users get Read-Only unless the operator chose a higher default role.
  • Hardened metadata parsing. Customer-supplied IdP XML is parsed with external entities and DTDs disabled.
